# Remote access: permission model as built, part 3

These notes were written as one file. "Above" and "below" in them can mean another part: the decision, the three permission parts, [`remote-access-listeners.md`](remote-access-listeners.md) and [`remote-access-ownership.md`](remote-access-ownership.md) are listed in [`remote-access-decision.md`](remote-access-decision.md), and [`threat-model.md`](threat-model.md) and [`household-access.md`](household-access.md) summarise them.

- **Diagnostics:** reads (overview, setup checks, install presets, GPU PyTorch status, model cache, pyannote readiness, job history, log, support report) are `admin.diagnostics`; `POST /api/diagnostics/gpu-torch/check` (also `admin.diagnostics`, so it gets the CSRF check) adds a CUDA check that imports torch in a fresh Python; one at a time, and 409 while any job, restore, cleanup or install runs (it takes a CUDA context). `POST /api/diagnostics/package-updates/check` is also `admin.diagnostics`: it is the only Diagnostics call that asks PyPI (one fixed `https://pypi.org/pypi/<dist>/json` per static dist name, with a timeout, at most once a minute and never two at once), runs only on an explicit click, and its cached answer is the exact version a later Upgrade installs: the upgrade body must carry the `target` the user confirmed when a check is cached, and is 409 when it is missing or the cache no longer says so (with no cached check it is a plain upgrade within constraints.txt); any install, upgrade or PyTorch setup drops the cached check; any install or PyTorch setup clears the cache, and a check that was still running then stores nothing. The library reset is `local_only()` with `confirm=true` and `confirm_text` "RESET" and refuses while a job runs; dependency install and upgrade (each re-planned on the server like `POST /api/diagnostics/dependencies/{package}/upgrade/plan` previews it, with the same accepted-risk, read-only-folder and restore-on-failure rules) and the GPU PyTorch setup are the same (`local_only()`, `confirm=true`, 409 while a job runs) but return a job id at once and run as the background job `dependency_install`, which holds the library exclusively until it ends or is cancelled through `POST /api/jobs/{job_id}/cancel` (this kills pip's whole process tree), with `GET /api/diagnostics/dependency-install` (`admin.diagnostics`) giving the package, the job and the redacted output tail and result; package names, the PyTorch variant's versions and its index URL come only from static server tables, and every other install/upgrade pins the installed torch family through a temporary constraints file. **Deno and Test first** (`api/routers/diagnostics_installs_routes.py`, Q02/Q06): their status reads (`GET /api/diagnostics/deno`, `GET /api/diagnostics/upgrade-check`) are `admin.diagnostics`; starting either (`POST /api/diagnostics/deno/install`, `POST /api/diagnostics/dependencies/{package}/test-upgrade`) is `local_only()` with `confirm=true`, refused (409) while any job, restore, cleanup or install runs, and runs as a background job (`deno_install`, `upgrade_check`) that in turn blocks installs. Deno comes from winget on Windows (fixed command) or from the official release zip in a static per-OS/CPU table: every hop is https on an allowlisted GitHub host (at most 5 redirects), every request has a timeout, the body is byte- and time-capped, the zip must match the release's own `.sha256sum`, and only the `deno` binary is unpacked to `~/.deno/bin`. Test first takes only the package the Upgrade route accepts and the target the last update check cached (409 otherwise); it installs that version into a throwaway environment and runs the tests there, never touching the real install. Output lines are redacted. **Install browser support** (`api/routers/diagnostics_browser_routes.py`): `GET /api/diagnostics/browser` is `admin.diagnostics` (booleans, MB and fixed text, no path); `POST /api/diagnostics/browser/install` is `local_only()` with `confirm=true`, refused (409) while any job runs, when Chrome or Edge or an app-folder Chromium exists, and (422) without the `playwright` package or with under 300 MB free. It runs the fixed argv `python -m playwright install chromium` as job `browser_install` with `PLAYWRIGHT_BROWSERS_PATH` set to the app's own `playwright_browsers` folder in the data directory, 15 minutes at most, the process tree killed on timeout or cancel; output is redacted (secrets, then paths) and only a 12-line tail is kept.
- **User administration and the audit log** (`api/routers/admin_users_routes.py`, branch `admin-audit-users`, 2026-09-30): listing users and reading the audit log are `admin.users.read`; deactivating, activating and ending a user's sessions, and giving or taking one member permission (`POST`/`DELETE /api/admin/users/{user_id}/permissions/{permission}`, the People card's Rights checkboxes, 2026-10-26; only on an active non-admin account and only the household-default and opt-in permissions, so it never makes or unmakes an admin and never touches the caller's own account) are `admin.users`, and the writes need the session's CSRF token with auth on; with auth off only the owner at the PC reaches them. On the single-port sign-in setup (the admin listener with auth on), remote writes are for non-admin accounts only (user decision 2026-09-30, "remote, non-admins only"; on the D5 household listener no admin write is served at all, below): an admin can lock out a lost phone's household account from anywhere, but deactivating, activating or ending the sessions of an admin account answers 403 unless the request is from the PC (`is_local_request`; D5: admin actions only from the PC), so a stolen admin session can't lock out the other admins. The 403 names the PC recovery commands (`python -m api deactivate` / `grant-admin`), and the People card (on the People and access page, a left-rail item in the System group) disables those buttons with the reason whenever the page isn't on the PC. Checks run in the order 404, own account (409), admin target away from the PC (403), last active admin (409). Guards (409): an admin can't deactivate their own account or end their own sessions (Sign out does that), and nobody, the local owner included, can deactivate the last active admin (one conditional `UPDATE`, so two admins can't deactivate each other at once). The local owner has no users row, so it can't be a target. Deactivating a user or ending their sessions deletes their session rows, so their open event streams re-check at once and end; it does not cancel jobs or Live sessions they already started. On the D5 household listener an admin session holds `admin.users.read` but not `admin.users` (below; user decision 2026-09-30, "block only writes", which supersedes "remote, non-admins only" there): it can view the user list (each account's email shown in full) and the audit log (emails in details masked as below) from away, and every write, including deactivating a non-admin account, answers 403 and happens at the PC (or on the single-port sign-in setup); from away, the household-account lockout is `python -m api deactivate` at the PC. The People card shows the list without its buttons when `/api/auth/me` lacks `admin.users`. The `python -m api deactivate` command stays unguarded as the recovery path (`grant-admin` restores an admin). Removing an admin's rights (`POST .../revoke-admin`, or `python -m api revoke-admin <email>` at the PC) is PC-only like every other change to an admin account, never your own account (409), and refused (409) for a non-admin or the last active admin (one conditional `UPDATE`, as for deactivate; the CLI is guarded too, since `grant-admin` is the undo, not a recovery need). The account stays active, gets the household default permissions if it holds no member permission, and its sessions end so its next request is a member's; audited as `user.revoke_admin`. Each write is audited by the existing `auth_service` functions (`user.deactivate`, `user.activate`, `session.revoke_all`, actor = the admin's user id, none for the local owner). The user list carries each user's email, flags, permissions and a live-session count, never session rows (no IP prefix, user agent or hashes). The audit view is newest first, at most 200 rows a page (`before_id` cursor), exact-match filters on action and user id, and read-only (no edit or delete route). Details are re-scrubbed on the way out (`redact_secrets`, long token-like runs, URLs and paths); the coarse IP prefixes the sign-in audit already stores (IPv4 /24, IPv6 /48) are shown as stored, and email addresses, such as the attempted one on a refused sign-in (`login.denied`), are masked to the first character and the domain (`j***@gmail.com`; a one-character local part or a value with no `@` shows no characters; user decision 2026-09-30). The stored rows keep the full address. No account creation, permission changes or sign-in configuration here.
- **Signed-in devices** (`api/routers/auth_routes.py`, branch `remote-access-wp3-device-sessions`, 2026-09-30): `GET /api/auth/sessions` lists the caller's own live sessions, `POST /api/auth/sessions/{auth_session_id}/revoke` signs out one of their other devices and `POST /api/auth/sessions/revoke-others` every device but the one asking. All three are `authenticated()` (any signed-in user, no permission; writes need the CSRF header), like `logout`: they act only on the caller's own sessions, because the user id comes from the caller's session, never from the request, and an id that isn't one of the caller's sessions answers the same 404 whether it belongs to someone else or doesn't exist. The session making the request can't be revoked there (409: Sign out also clears this device's cookies). An admin may list their devices from anywhere, but both revokes answer 403 for an admin unless the request is from the PC (`is_local_request`; D5: anything involving an admin account is PC-only, so a stolen admin session can't sign the owner's other devices out), and the card disables them with that reason away from the PC; a non-admin may sign out their devices from anywhere. With auth off they answer 404 (the local owner has no sessions). A list row carries the session's row id (not its token), a coarse device label built from a fixed list of browser and system names ("Chrome on Android", `auth_service.device_label`), the created/last-used/expiry times, the IPv4 /24 or IPv6 /48 prefix already stored, and whether it is this device: no token, hash, user agent or full address. New sessions store only that label (the raw user agent is no longer kept); `init_db` labels sessions from before this from their stored 60-character user agent prefix and then blanks it. A revoke deletes the session row, so the device's next request is a 401, and wakes that user's open event streams to re-check their session at once (`event_stream_service.request_recheck`; sign-out, admin revoke and deactivation do the same), so a lost device's live updates stop immediately. "Sign out all other devices" also rotates the caller's own session: a new session row with a new token and CSRF token (both cookies set again; the sign-in time and expiry carry over, so it never extends the session) replaces the old row, so a copy of this device's cookie taken earlier stops working too; this device's own event stream re-checks, ends and reconnects with the new cookie. The card also suggests removing a lost phone from the Google account, since it may still be signed in to Google and could sign in again. Audited as `session.revoke` (`session <id> ip <prefix>`) and `session.revoke_others` (`user <id>: <count> ip <prefix>`, only when at least one other device was signed out), actor = the caller. Timeouts: a session ends after `BAIHE_API_SESSION_IDLE_DAYS` (default 14, 1-90) unused and `BAIHE_API_SESSION_MAX_DAYS` (default 30, 1-365) after sign-in, both checked on every lookup, so a shortened setting also ends older sessions. Every sign-in already creates a fresh session and revokes the one the browser presented (rotation, step 134), and sign-in stays rate-limited per address and per /24 or /48 (unchanged). Admin-side session control is unchanged: the Users section's session count and "Sign out everywhere" (`admin.users`, admin targets PC-only, D5). The React Settings page shows a "Signed-in devices" card to a signed-in user.
- **Extension bridge control** (status, on/off, token) is `local_only()`: the bridge and its token belong to the owner at the PC (user decision 2026-09-29). The status never carries the port or the token; only `POST /api/extension/token` with `confirm=true` returns the token, with `Cache-Control: no-store`. Port 8756 stays loopback-bound. The extension's translation engine and model (inventory G16) are a PC-side app setting: reading them is `admin.settings` (engine names and key presence only), saving them is `local_only()` like every settings write; the key is resolved from .env on the PC for each page and is never returned or sent to the browser.
- **Library admin** (`api/routers/library_admin_routes.py`, #385): bulk status and tags, the storage scan and artifact info are `admin.library`; bulk translate is `jobs.start` (plus the engine check), like any other translate run; bulk delete, export zip, backup, artifact download, restore and storage clean are `local_only()` with `confirm=true` and a typed word (DELETE, RESTORE, CLEAN), because they remove data or hand out whole-library files. The React Library admin (#385) hides the PC-only actions away from the PC (`usePcOnly`). The backup of one person's items (`POST /api/library/admin/backup/user`, body `user_id`, omitted for the items owned at the PC) is `local_only()` too and uses the same artifact download (kind `user_backup`, a fixed file name that never carries the person's name; only the newest such file is kept, and a cancelled run leaves none). It is built from a copy of the database; the live library is only read. The copy keeps that person's dramas and series and the rows that belong to them, their own translate history, household presets and known titles, and drops every other drama's and series' rows, all auth data (users, permissions, sessions, audit log), job state, caches, benchmarks, the voice bank and app settings (every table is classified in `library_admin_service.USER_BACKUP_TABLES`; an unclassified table is left out and fails a test). A series goes with its owner (glossary, characters, translation memory); another person's drama in it stays behind, and the person's drama in someone else's series comes without that series. Only the kept dramas' own folders are zipped: no other drama folder, voice bank clip, benchmark file or `sources.db`.
- **Routes that return line text need `lines.read`** (security audit fixes, owner decision 2026-10-11), on top of their own permission where they have one (`library.read + lines.read`, `review.use + lines.read` in `docs/route-permissions.md`). `lines.edit` does not imply `lines.read`: someone who may edit lines but was not given `lines.read` still cannot read line text. The Reader page moved from `library.read` to `lines.read` on 2026-10-10; `db._grant_lines_read_for_reader_page` grants it once to every account that held `library.read` at upgrade, so nobody lost the Reader, and the `migrations.reader_page_lines_read` marker keeps a later revoke.
- **Reader** (`api/routers/reader_routes.py`, used by the React Reader, #388; contract decided by the user 2026-09-29): overview, notes, media availability (booleans only, no bytes), vocab and wiki lists are `library.read`; the page HTML (`GET .../page`; owner decision 2026-10-10, with a one-time `db.init_db` grant of `lines.read` to every account that held `library.read`, marker `migrations.reader_page_lines_read`), caption tracks and every export (vocab CSV/.apkg, wiki Markdown) are `lines.read`, since they carry line text; progress, notes, lookup, rich-export queue and wiki clear are `lines.edit`; the LLM story tools, wiki update and Q&A are `jobs.start` plus `require_engines_allowed` (an omitted engine counts as paid), and lookup with `use_llm` also needs `jobs.start` and the engine check. Media bytes stay `media.stream`.
- **Comic viewer** (`api/routers/comic_routes.py`, Scanlate S1 read paths; lead decision 2026-09-29): the page list and the page resume point are `library.read`; page images are `media.stream` (opt-in, so a household user sees an "ask for media access" state until granted); text regions carry translated text, so `lines.read`; saving the resume page is `lines.edit`, as the Reader's progress is. Progress is the default profile's, shared by every API user.
- **Scanlate automatic path** (`api/routers/scanlate_routes.py`, branch `scanlate-auto-pipeline`, 2026-09-30): the panel config (engines with key booleans only, cached-model flags, the saved OCR backend, upload limits) and the per-page run notes are `library.read`; one page's detail carries its region text, so `lines.read`; the page upload is `local_only()` (uploads are PC-only; PNG/JPEG/WebP/PDF with the caps in `services/scanlate_pages_service.py`, Content-Length checked before the body is read, body stream counted); the run (detect, OCR, translate, typeset), the re-render and the ZIP/PDF export are `jobs.start` jobs (`scanlate_<drama_id>`, poll/cancel via `/api/jobs`), and the run also calls `require_engines_allowed` on the engine it will use (the request's, else the Settings default, resolved before the check, as shorten-overlong). Keys, the HF token, the OCR backend and the Tesseract program come only from the PC's saved settings; `{page_id}` is nested under `{drama_id}` and scoped by `db.get_page(page_id, drama_id=...)`. Export downloads use the existing `GET /api/artifacts/dramas/{drama_id}/{kind}` (`media.stream`) with the new kinds `scanlate_zip` / `scanlate_pdf`. Rows above added by hand on this branch (not regenerated).
- **Voice-clone setup** (`api/routers/voice_clone_routes.py`, parity blocker #7): uploading and removing a character's reference clip are `local_only()` (uploads and deletes are PC-only); starting a candidate extraction is `jobs.start` (local ffmpeg only, no paid engine); listing candidates is `lines.read` (each carries its matched line's text); playing one is `media.stream`; choosing one is `lines.edit`, because it writes no client bytes (it copies a clip cut from the drama's own audio, like the voice-bank apply) and sets one speaker's fields; saving to the voice bank is `admin.library`, like the voice-bank rename; the series-character link is `lines.edit`, like the other character fields.
- **Public:** `/api/health`, `/api/meta` and the frontend shell catch-all (static files only; it never answers an `/api` path with data).
- **Extension device tokens** (`api/routers/device_token_routes.py`, `services/device_token_service.py`, table `extension_device_tokens` in `device_tokens.py`): `GET /api/auth/device-tokens` and `POST /api/auth/device-tokens/{device_token_id}/revoke` are `authenticated()` (the caller's own tokens; someone who lost `extension.send` can still list and revoke theirs), `POST /api/auth/device-tokens` (create) is `extension.send`, and everyone's tokens are listed and revoked at the PC only: `GET /api/extension/devices` and `POST /api/extension/devices/{device_token_id}/revoke` are `local_only()` (like the rest of `/api/extension/*`, which Caddy also refuses), so the household listener never serves them, not even to an admin. With sign-in off the own routes answer 404 (the local owner has no account) and the PC owner uses the PC-only ones. A token is `baihe_dt_` + 32 random bytes (urlsafe base64), returned once by create with `Cache-Control: no-store`; only its SHA-256 is stored (like session ids, a 256-bit random value needs no slow or keyed hash) and re-compared with `compare_digest`; `redact_secrets` scrubs the prefix. Label 1-40 characters (no control characters), expiry 1-365 days (90 when omitted; only an explicit null means never), at most 10 live tokens per user (checked inside one write transaction), 5 creates per user per hour; revoked or expired rows are pruned 30 days later at the user's next create. An id that isn't one of the caller's live tokens is the same 404 whether or not it exists. An admin account's own tokens are added only at the PC (D5); anyone, an admin included, can revoke their own from anywhere (it only removes access, and a lost laptop is away from the PC), while revoking someone else's stays PC-only. Audited: `device_token.create` (`token <id> ip <prefix>`), `device_token.revoke`, `device_token.admin_revoke` (`token <id> user <id>`), `device_token.revoke_all` (`user <id>: <count>`), never the token or label. Losing `extension.send` (permission revoked, admin rights removed without a stored grant) or deactivation revokes every token of that user, so a later re-grant doesn't revive one. `api.auth.require_device_token()` (declaration kind `device_token`, used by no route yet) reads only `Authorization: Bearer` (exactly one header; never a cookie or query string), refuses a malformed, unknown, revoked or expired token, or an inactive user, with the same 401, and is throttled on failures only (20 per client bucket and 100 per IPv4 /24 or IPv6 /48 per 10 minutes, then 429 for a token that doesn't verify; a token that verifies still works from such an address, and a request with no `Authorization` header is neither counted nor blocked, so a revoked laptop that keeps retrying can't lock out valid tokens behind the same address). The principal is the token's user with member rights only (no `admin.*`, no admin override, even for an admin account), then `listener_principal` and the drama/series path guard as for a session; it needs `extension.send` (403 otherwise), re-read every request. Last use (time and IP /24 or /48) is written at most once a minute per token. A library restore keeps the live library's tokens and never takes them from the upload (`auth_service.RESTORE_LIVE_TABLES`), so an old or crafted backup can't revive a revoked token or plant one; a user backup leaves them out. `EarlyAuthGate` still 401s any non-public `/api` path without a session, so the bridge routes will have to be exempted there by their declaration. Every session-revoking path also revokes the user's device tokens (`auth_service.revoke_all_for_user`, so admin revoke-sessions too; the one exception is `revoke_admin`, which ends every session but keeps the tokens when `extension.send` is still held through a stored grant, since tokens carry member rights only; and `revoke_other_sessions`: Sign out all other devices keeps the current session but not the user's tokens), as do deactivation, losing `extension.send` and the `python -m api deactivate` command, which goes through `auth_service`; revoking one session or signing out this device leaves them. `tests/test_device_tokens.py` walks every route of the single-port sign-in app and the household listener with a valid device token and expects 401/403 on each, and checks that a session cookie never satisfies the device-token dependency. A token is accepted only by `/api/ext-bridge/*` (`require_device_token()`, see `docs/browser-extension.md`): the member sends into titles they can edit, sees titles they can see, the translation engine is the owner's so a member without `engines.paid` is held to the free engines (`require_engines_allowed`), the monthly cap applies, and engine or detector error text never reaches the member.
- **Sign-in (step 134, slice A1, `api/routers/auth_routes.py`):** `GET /api/auth/login` and `GET /api/auth/callback` are `public_route()` and rate-limited in three tiers, each per 10 minutes: 20 per client bucket (IPv4 address, IPv6 /64), 40 per IPv6 /56 and 200 per IPv4 /24 or IPv6 /48; there is no global cap, so no number of networks can lock everyone else out. Accepted trade-offs: someone sharing your IPv4 /24 or IPv6 /48 (for example the same mobile carrier) can block sign-in for that prefix while they flood it, and your own retries meanwhile use up your bucket (sessions already signed in and the PC itself are unaffected); and without a global cap, many networks together can drive more Google token exchanges with junk codes; `GET /api/auth/me` is `public_route()` and returns only `{auth_enabled, signed_in, sign_in_configured, zone, user, permissions}`, never a token, the client id, the secret or the public URL. `authenticated()` is a fourth declaration kind meaning "any signed-in user, no permission, CSRF still required", allowed only on routes that act on the caller's own sessions and own device tokens: `POST /api/auth/logout` and the three signed-in-device routes (`GET /api/auth/sessions`, `POST /api/auth/sessions/revoke-others`, `POST /api/auth/sessions/{auth_session_id}/revoke`; see "Signed-in devices" above), and `test_authenticated_only_on_own_session_routes` pins it to those six (the four session routes and the two own-device-token routes). With auth off, login, callback and logout answer 404 and `/me` reports the local owner.

Deployment note (Caddy): Caddy must target the household listener, `reverse_proxy 127.0.0.1:{$BAIHE_API_HOUSEHOLD_PORT}` (for example 8610), **never 8600**: 8600 (`BAIHE_API_PORT`) is the PC's own admin listener (see [`remote-access-listeners.md`](remote-access-listeners.md)). Pointed at 8600 by mistake, every proxied request is refused (off mode's `LoopbackOnlyGate`), but that is a backstop, not the design. Run the API with `BAIHE_API_AUTH=off` (it applies to the admin listener) and `BAIHE_API_HOUSEHOLD_PORT` set; the household listener always has sign-in on. Caddy's defaults set `X-Forwarded-For`/`-Proto`/`-Host` and pass the public Host through; keep them: the household listener treats every request as remote whatever its headers say, but `client_ip` (sign-in rate limits, audit) uses the rightmost `X-Forwarded-For` entry. Never route 8600 or 8756 from the router either. The template is `deploy/caddy/Caddyfile.template` (it sets those three headers itself from the connection, drops `X-Baihe-*`, refuses a path with a `.`, `..` or empty segment, and refuses every `local_only()` route and every admin path except the two admin views (`GET`/`HEAD` `/api/admin/users` and `/api/admin/audit`) at the proxy as defence in depth, since the household listener refuses them itself; `tests/test_caddyfile_template.py` checks it against this table); the step-by-step guide is [`household-access.md`](household-access.md).
