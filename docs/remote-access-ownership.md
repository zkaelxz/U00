# Remote access: ownership and sharing

These notes were written as one file. "Above" and "below" in them can mean another part: the decision, the three permission parts, [`remote-access-listeners.md`](remote-access-listeners.md) and [`remote-access-ownership.md`](remote-access-ownership.md) are listed in [`remote-access-decision.md`](remote-access-decision.md), and [`threat-model.md`](threat-model.md) and [`household-access.md`](household-access.md) summarise them.

## Ownership and sharing (auth slices B1 and B2) as built

B1 (`services/ownership_service.py`, #414) added `owner_user_id`/`is_private` on dramas and series, the visibility rule (auth off, the local owner and admins see everything; otherwise a series is visible to its owner or when it is not private, and a drama to its series' owner, else not if its series is private, else to its owner or when it is not private) and the share-by-default setting. B2 (branch `auth-b2-ownership-enforcement`, 2026-09-29) enforces it at the API. A denied item is always a 404, identical to a missing one.

- **Path guard.** `require_permission` runs `api.auth.require_path_visible` after the permission check: any `{drama_id}` or `{series_id}` path parameter the caller can't see is a 404. One central check covers every such route (159 at the time) and every new one. Child ids under those paths (lines, terms, notes, history, versions, pages, characters, clip candidates, bulk jobs) were audited and are already scoped to the parent by their services. `local_only()` routes are the local owner and see everything. Editing is visibility-based (user decision 1), so reads and writes share the guard. `tests/test_api_ownership.py` has the static half (every owned route has a guarded declaration; any other path parameter must be nested under one or be listed in `OWNERSHIP_EXEMPT_PARAMS` with a reason) and a route walk: user B gets 404 on every drama/series route for user A's private drama and for a drama in A's private series.
- **Disk usage (`/api/data-usage`).** All nine routes (scan a folder of the app's data folder, move one item into Baihe's Trash folder, move the automatic-backup folder, list the Trash, restore from it, permanently delete one Trash item, empty the Trash, list unused voice clips, move unused voice clips to Trash) are `local_only()`: they read, move and delete files on the PC, and Caddy refuses `/api/data-usage*` too (the `@pc_only` matcher). Paths in requests and responses are relative to the data folder (never absolute, never the data folder's own path); the only absolute path is the move `destination` the owner types, which is not echoed back. The path guard has no id to check, so `services/disk_usage_guard.py` validates every path: no `..`, absolute path, drive letter or `:`, trailing dot or space, and every component must exist as an ordinary file or folder (a symlink or junction anywhere on the way is refused, never followed; a link inside a scanned folder is counted as itself, not entered; the folders links point at are measured apart, read-only and within the scan's budget, and reported only as a size and file count in `linked_bytes` / `linked_files` / `linked_complete`, never as a path, so a folder shows the same numbers from its parent and when opened. A link whose target is inside the data folder adds nothing (it is counted where it lives), a target that holds the data folder, the program folder or the user's folders is skipped, a target is counted once per scan, so a second item linking to the same (or a containing or contained) target shows less than it would opened alone and is reported with `linked_complete=false`, links inside a target are not followed, and at most 64 linked folders are measured per scan. Link targets are checked hop by hop against an allowlist (relative, `X:\...`, `\\?\X:\...`, `\\.\X:\...`) before anything is opened, and so is every folder on the way to a hop (a symlink there is followed only if its own target passes); UNC, `\\?\GLOBALROOT`, pipe and `\\?\Volume{}` targets are never opened and make `linked_complete` false. A folder on another volume is treated as a link, so it is refused for clear and move). Server-enforced protection for clear and move: the data folder itself, the live SQLite files (`-wal`, `-shm`, `-journal` too), `.env` and key files, the INSTALLED/PORTABLE markers, saved site sign-ins, installer files, anything in the program folder, the Trash folder, and any folder holding one of those. Both refuse (409) while any background job, restore or maintenance run holds the library, and while the GPU lock has a live holder: a tool run outside the server that writes no `job_records` rows (`python -m tools.asr_bench`) is detected only while it holds the GPU lock. Known limit: such a tool's non-GPU work leaves no trace and is not detected (the headless CLI that had the same limit was removed in #1345). Clear and move also refuse when the data folder is a drive root, the user's home, a folder holding it or a shell folder (Documents, Desktop, ...), for a folder that couldn't be read fully (paths of MAX_PATH or longer and names ending in a dot or space count as unreadable) or that holds a link, and for top-level entries Baihe doesn't create (shown, protected as "Not created by Baihe"). Items that can't be recreated (a title's media, saved voice samples and benchmark cases, `library/source_profiles`, `saved_comics`, and every backup copy under `library/backups`) also need `confirm_irreplaceable`. Clear needs `confirm=true` plus the size and file count the user saw (409 when the item changed) and does not delete anything: it renames the item, atomically and on the same volume, into `<data folder>/baihe_trash/<id>/payload` and writes a `manifest.json` beside it (original relative path, kind, size, file count, time); it refuses when the item is on another volume or the new path would reach MAX_PATH, and never copies. The Windows Recycle Bin is not used: the installed API runs as a service account, so its bin is not the owner's. `GET /trash` takes no lock shared with the scan. Restore renames the payload back to its original relative path under the exclusive hold, only when every folder on the way still exists with no link, the place is free, it would pass the clear protection checks, and no job runs (409 with a plain reason otherwise). The only permanent deletes in the feature are `trash/purge` (one entry; needs the typed word `DELETE` exactly and the size shown, 409 when it changed; the size is `null` only when the list showed it as unknown because the walk limit was reached) and `trash/empty` (needs `DELETE` plus `expected_item_count` and `expected_size_bytes` of the list shown, both required, 409 `changed` when they differ or the Trash is too large to measure completely): they act only on folders directly inside `baihe_trash` whose names match the id pattern (`YYYYMMDD-HHMMSS-<8 hex>`), refuse the Trash root or an entry that is a link or reparse point, run under the exclusive hold, delete with a walk that unlinks links without following them (on POSIX relative to open folders, so a folder swapped for a link after it was listed can't redirect a delete; on Windows path by path with a check before each step, a residual window that needs write access to the Trash folder) and removes folders bottom-up (clearing a read-only bit only on ordinary files and folders, never through a link), and on any failure keep what is left in Trash and return a generic error with no paths. Move works only for the automatic-backup folder (through `auto_backup_service.set_settings`, which moves the copies and saves the setting together); the destination must be an existing real folder outside the data and program folders. The scan is a bounded read-only walk (2,000,000 entries or 30 s, then `partial=true`) run in the thread pool. Unused voice clips (`GET /unused-voice-clips`, `POST /unused-voice-clips/to-trash`) offer only files named `clone_ref_*` or `clone_pick_*` directly inside a title's `voice_refs/` (voice-bank copies are written to the title's root folder, so they are not offered) that no `characters.ref_audio_filename` of that title matches (by last name part, ignoring case) and no live speaker-merge undo record holds (a hook that is empty until those records exist), for a title with no running dub, narration or audiobook job. A response carries the title, file type, size and date plus an opaque id (an HMAC of title id and file name under a key made at process start): no file name or path, and an id from another title or an earlier run matches nothing. Moving needs `confirm=true` and each clip's shown size, then looks every id up again under the exclusive hold, checks it is still unreferenced and unused by a job right before the rename and once more right after it (putting it back, without overwriting anything already there, if a speaker picked it in between), all under that title's clip lock, which clip upload, remove and choose also take around their file check and database write, and uses the same Trash rename, so it can be restored. A clip that changed is skipped, not an error; a batch that stops part-way (library busy, Trash move failed) returns the error with `details.moved_count`, `moved_bytes` and `skipped` for what was already moved, and the request takes at most 500 clips (the UI sends larger selections in batches). This route deliberately needs only `confirm=true` and the shown sizes, not `confirm_irreplaceable`: the files go to the restorable Trash and a permanent delete still needs the typed word `DELETE`. There is no automatic expiry of Trash.
- **Backups (Step 43, redefined 2026-09-29).** Every `/api/backups/*` route (auto-backup settings, back up now, the rotating copies' info and a copy's dramas, restore one drama, delete one copy or all) is `local_only()`: backups and restores are PC-only. None takes a path parameter; the drama to restore is a body field (`drama_id`, an id inside the copy, not a live drama), so the path guard has nothing to check. A copy is chosen by its file name (`snapshot`, a query or body field), which the service only matches against the backup folder's own listing of copy files and never uses as a path; responses name copies by file name, never by path. Restore and delete need `confirm=true` plus the typed word (RESTORE, DELETE); deleting every copy also needs an explicit `all=true`, and a delete naming neither a copy nor `all` is refused. `all=true` deletes only the copies this library manages (its id in the manifest and recorded as written by it); a copy it doesn't manage (another library's in a shared folder, a hand-copied library's with the same id, an untagged or unreadable one) is deleted only with `include_unmanaged=true`, by name or with `all`. With no copy named, the dramas list and the restore answer 409 with `details.reason = "choose_copy"` and the candidate copies (name, created_at, sequence, size, managed: names only, no paths) when the newest copy can't be told for sure. The snapshot never holds `.env` or keys (they live outside the library, and the backup writer skips any `.env`), and the snapshot folder is inside `backups/`, which every backup excludes. `POST /api/backups/import/list` and `POST /api/backups/import` take an uploaded backup file (a snapshot copy, a manual backup zip or a bare `library.db`) and are also `local_only()`: the upload's Content-Length is checked against `BAIHE_MAX_UPLOAD_MB` before any of the body is read (chunked bodies are refused) and the body stream itself is counted; the file's database is read only from ordinary tables, under a time limit; the import needs `confirm=true` plus `RESTORE` and is refused while a backup, export, restore or cleanup runs. Every imported drama is new, owned by the acting user and private per their sharing default (never taken from the file); a stored file name (audio, cover, pages and the like) is kept only when it names a file inside the new drama's own folder and that drama's files came with the import, otherwise it is cleared; responses carry ids, titles and counts, no paths.
- **Lists.** Library `/dramas`, `/stats`, `/recent`, `/costs`, `/series`, `/search` (line text) and `/history` show only visible dramas (`db.drama_visible_sql`, the SQL twin of the rule, shared with `db.list_dramas`). Stats and spend count only visible dramas; spend not logged against a drama is left out for household users. Translate history is per user: a household user sees their own rows; rows with no user (the PC, the extension) are for admins and the local owner. `POST /api/translate` now stamps the user.
- **Drama ids in bodies.** Bulk translate reports a drama the caller can't see as `not_found`, like a missing one. Source chapter and URL imports and tracking a series into a drama 404 on one the caller can't see.
- **New items.** `drama_service.create_drama` (API create, Discover import-to-library) stamps `new_item_defaults`: the creator, private unless they share by default. Sharing by default is off unless the person turns it on (user decision 2026-09-30): the local owner's household setting and a user with no stored value both mean private, and a new user starts with it off. Existing accounts were switched to private once by `init_db` (their stored 1 came from the old column default, which nobody could change); a choice made after that is kept (marker `migrations.share_by_default_off`), and existing items keep their flags. Items created at the PC or with sign-in off have no owner and are stored private, so once sign-in is on the household sees them only after an admin shares them (Settings > Sharing notes this and can filter to them). New series were already stamped by `get_or_create_series_for`. The CLI creates none.
- **Jobs.** With auth on, `ActingPrincipalMiddleware` gives each request a holder that `require_permission` fills, and `jobs/job_launch.py`'s `start_job`/`start_process_job` record that user as the job's owner (memory and `job_records.owner_user_id`). A job started outside a request (a job's own threads) is the PC's. `ownership_service.can_see_job`: admins, the local owner and auth off see every job; otherwise a `<prefix><drama_id>` job (`background_jobs.DRAMA_JOB_PREFIXES`) follows its drama's visibility, for its starter too (a drama that goes private stops showing them its jobs), and any other job is visible only to its starter. `/api/jobs` lists only those; GET and cancel of any other are 404. Cancel and force stop (owner decision 2026-10-12, `ownership_service.may_cancel_job`, the same function behind each job's `owned_by_me`, so the Cancel button is offered exactly where it works): a member may stop a job they started, and any job on a title they own, including one with no recorded starter (one a job's own thread started, such as `bulk_series_translate`'s `translate_<id>`); another member's job on a shared title they merely see is a 403. A job with no title and no starter (started at the PC, and rows from before starters were recorded) is stopped only by an admin or the PC owner. The title-scoped cancel routes (glossary extraction and spelling suggestions, through `jobs_service.cancel_job`) use the same rule; a bulk translation batch records no starter, so only its title's owner and admins may cancel it. A route declared only `jobs.cancel` checks that its `{drama_id}` is visible, not editable, so an admin away from the PC can stop a job on a member's private title. Admins (on the household listener too) and the PC owner may stop every job. The cancel touches only the run that was checked: a shared job id (`sources_search`, `bulk_series_translate`...) that someone else restarted in between answers 409. Jobs wait in one line, the GPU queue; `GET /api/jobs/queue-summary` (`library.read`) gives everyone the counts of running and waiting jobs and gives each caller the place in that line (1 = next) of their own waiting jobs (`owned_by_me`), never another user's job id, name, title or owner. Counts cover every process; places only this server's GPU queue. The fixed-id results (Discover bulk-extract and navigation-help, Sources search, URL preview, series and import jobs) and Live sessions (list, status, stop) use the same rule, except that a fixed-id result nobody may see answers 200 with status `idle`, the same as when nothing has run (a Sources import into a drama the caller can't see stays 404, like the drama). The per-drama auto-tune and glossary-extraction status reads answer `idle` too when no run is held.
- **Jobs that replace existing text or speakers also need `lines.edit`** (owner decision 2026-10-10). The route stays `jobs.start`; the service checks the acting principal (`ownership_service.require_acting_lines_edit`, 403) only when the request would overwrite: a transcribe run on a title that already has lines (`POST /api/transcribe/dramas/{id}/run`), diarization with `overwrite_manual=true`, a translate run with `force_retranslate` over lines that already have English (and the glossary-affected run, which force-re-translates through the same service), and fix-flagged (`POST /api/review-jobs/dramas/{id}/fix-flagged`). A first transcription of an empty title and translating untranslated lines stay `jobs.start` only.

Judgement calls (for the planning session):
- **Central guard instead of a per-route dependency.** The spec's option 1 (plan section B, enforcement point 1). It needs no change per route and covers new routes by default; the static test fails if a route names a drama or series under another parameter name.
- **Cancel is the starter's, the title owner's or an admin's** (owner decision 2026-10-12, replacing "cancel follows visibility"): seeing a shared title's job no longer lets a member stop it. See "Jobs" above.
- **Shared fixed job ids stay shared.** Two users can't run Discover bulk-extract, navigation help or a Sources search at the same time (the second gets 409 or 429, as before), and a new Sources run replaces a finished one. The owner check means nobody reads another user's result. Per-user job ids would remove the wait; not done, to keep the change small.
- **Tracking a series** still relies on the process's latest `sources_series_<source>` result, whoever loaded it. It reveals nothing new to the caller (they name the series), so it isn't owner-checked.
- **Push (SSE, `GET /api/events`, `library.read`, user decision 2026-09-30 "SSE everywhere"):** one stream per tab carries job changes, the bell list and Live status, with the permission of the three GET routes it replaces (`/api/jobs`, `/api/notifications`, `/api/live/sessions`). Hooks in `background_jobs` and `notification_service` only name what changed; every event is re-read through the GET route's own service call with the stream's principal (`services/event_stream_service.py`) and serialized through the GET response model, so visibility is exactly the GET routes' and anything hidden is skipped (a `job_gone` is sent only for a job id that stream already showed). With auth on the session is re-checked at most every 5 s (before a batch or heartbeat), without counting as activity (`resolve_session(touch=False)`), and the client closes the stream while its tab is hidden, so an open tab never keeps an idle session alive; sign-out or a revoked `library.read` ends the stream. One process-wide sweep of `job_records` (a few columns, every 5 s while any stream is open) catches jobs other processes run. Live events carry status only (`cues: []`); cue text still comes from the GET. Caps: 6 streams per user (or the local owner), 32 in total (429 beyond, the client polls instead); per stream at most 64 pending ids, then one `resync`; a stream closes after 30 minutes and the client reconnects. A `ping` event after 15 s of silence (the client treats about 45 s of silence as a dropped stream), `Cache-Control: no-cache`, `X-Accel-Buffering: no` (Caddy/nginx). EventSource sends the session cookie and no custom header; a GET needs no CSRF token. Keys, paths and other users' data never appear (the same projections as the GET routes).
- **Merging two speakers (`POST /api/characters/dramas/{drama_id}/merge-speakers` and `/undo`, `lines.edit`).** Deleting the merged source Characters row is an ordinary lines edit of that drama, not a series-person removal: `series_characters` is never touched, and the undo is a server-side, single-use record scoped to the drama and the user who merged, so no Characters row or clip name reaches the browser. Clip files: no merge, undo, rename or Characters-field edit deletes a clip file from `voice_refs/`, whatever its kind (upload `clone_ref_`, pick copy `clone_pick_`, voice-bank copy), since removing files is PC-only (`local_only()`). Choosing a candidate still replaces the speaker's own previous `clone_pick_` copy for good, as before (never an upload). A clip left behind, including a merged-away speaker's pick or upload, is listed and removed by the PC owner from Library tools > Storage (restorable Trash). A clip that a live undo record (unexpired, not retired) would give back counts as in use there (`db.live_speaker_merge_undo_clips`). Expiry and retirement of undo records touch database rows only; a merge retires earlier undos for either speaker inside its own transaction, and the bookkeeping after a commit is best-effort and never changes the response. The request needs `confirm=true`.
- **Household-wide by decision (plan B, point 6):** voice bank, presets, Discover known titles, tracked sources and notifications. The header bell list (`GET /api/notifications`, `library.read`, Step 44 item 5) follows the same split: its new-chapter events are household-wide, and a job-ended event is listed only to a caller who can see that job (`ownership_service.can_see_job`, as `/api/jobs`); it carries no job id, path or line text. Event ids are millisecond timestamps, not a counter, so a gap says nothing about hidden events; 500 events are kept so other users' jobs don't push a viewer's own out of their 50. A Discord/ntfy push (the PC owner's channel, which the household may share) names a drama only when a household member could see it: a private drama's (or private series') title is left out (security review, 2026-09-30). `GET /api/sources/tracked` lists every tracked series, but a linked drama the caller can't see is reported as `drama_id: null`.
- **Monthly spend is household-wide.** The translate config's `month_spend` (and the monthly cap checked before a run) is the whole library's spend this month, not the caller's: the cap is one household budget. It is a single total, so it names no drama; the per-drama cost lists are filtered (Lists above).
- **Queued GPU jobs don't say what they're waiting for** (review M-1). The message used to name the running job ("GPU busy with Ollama translation (<title>)"), which leaked another user's private drama title to anyone who could see the waiting job, and was mirrored to `job_records`. It is now always "Waiting for the GPU (another job is running)", on the PC too; naming the job only when every viewer of the waiting job could see the busy one wasn't worth the complexity.
- **The API always passes a principal.** Services keep `principal=None` as "auth off". Instead of failing closed on None, `tests/test_api_ownership.py` checks statically that every call from `api/` to such a service passes a principal (the routes pass `request.state.principal`, which `require_permission` always sets, to the local owner's principal with auth off), and that every job or Live-session route is listed with the owner check it uses.
- **Sharing controls** (`api/routers/sharing_routes.py`, branch `admin-sharing-controls`): `GET /api/sharing/items` (every series and drama with its owner's display name, never an email, its Shared/Private flag and series membership; paged, at most 200 a page) is `admin.library`, so admins only (the local owner with auth off). Making one item private or shared (`POST /api/sharing/{dramas|series}/{id}/private`) is `lines.edit`: the path guard 404s an item the caller can't see, then `ownership_service.set_private` allows only its owner or an admin (403 otherwise) and refuses a drama in a series in either direction (it follows its series), a series holding someone else's drama, and, for a non-admin series owner, a series holding a drama owned at the PC (409). Every flip that is written is audit-logged (`sharing.set_private`, ids only). Reading one's own "share new items" setting is `library.read`; changing it is `lines.edit` (only people who can create or edit items need it). With auth on, the owner at the PC signs in like anyone else to use these.
- **Discover import's duplicate check** (`admin.library`, so an admin) still looks across every drama.
