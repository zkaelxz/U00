# Remote access decision (replaces D6: Tailscale)

Decided by the user on 2026-09-29, from a discussion session. No repo changes were made by that session; this file records the outcome.
It replaces D6 (Tailscale + Tailscale Serve) in [`migration-review.md`](archive/migration-review.md) and supersedes [`remote-access-design.md`](archive/remote-access-design.md).
**D5 stays** (admin actions are PC-only, on a separate loopback listener); built, see [`remote-access-listeners.md`](remote-access-listeners.md).

**Key entry (decided 2026-09-29):** the launcher (`start.bat`) sets `BAIHE_API_ALLOW_KEY_WRITES=1` unless the user already set it (an explicit `0` opts out), so API keys can be entered in the React Settings form at the PC, or by editing `.env`. Key writes stay `local_only()` and still require a direct loopback peer and Host, no proxy headers, and Origin, if sent, is loopback (`api/routers/settings_routes.py:_require_local_admin`); values are written to `.env` and never returned. `python -m api` started directly leaves the flag off.
Status: sign-in, ownership, the D5 listeners and sharing are merged; the files listed under "Where the as-built detail is" describe them as built. Left for the owner: the LAN test with a real certificate and the router port. Implementation steps are proposed as 133-140 in [`baihe-roadmap-master.md`](archive/baihe-roadmap-master.md) section 5.

## Context

- The user doubted the VPN, so Tailscale is out.
- The PC is always on with a normal home IP. The user owns a domain.
- Household members use their own phones and computers, browser only.
- Today `api/server.py` has no authentication, and the API binds to loopback by default.

## Decided

- **Route:** Caddy on the PC with a real Baihe login. Household devices will stream and download large video; Cloudflare's request cap and its terms on large media are uncertain, and the extension behind Cloudflare Access is unproven.
- **Order of work:** build auth and permissions, test on the LAN through Caddy with a real certificate, and open the router port last.
- **Auth:** Google OIDC sign-in (a vetted library such as Authlib) plus a Baihe users allowlist. Match on Google's `sub`, require `email_verified`, use PKCE, state and nonce. Server-side sessions in a Secure, HttpOnly, SameSite cookie, with CSRF protection. Rate-limit login routes; audit-log sign-ins and admin actions. The first admin is granted locally with `python -m api grant-admin`, which also serves as recovery.
- **Permissions:** deny by default, one declared permission per route, and a static test that fails if a route has none.
  - Household scope: browse, read, review, edit lines, and start jobs on media already on the PC, and cancel their own (owner decision 2026-10-12, under "Jobs" below).
  - Separate permissions, off by default: `media.import_url` (yt-dlp), `sources.import` (manga and novel fetch), `engines.paid`, `extension.send`, `media.stream`.
- **Keys:** unchanged. Entered at the PC, resolved server-side, never sent to a device. Slice 24 stays off by default.
- **Admin:** stays on a separate loopback listener (D5) that Caddy never routes to. Remote admin, if ever wanted, would need identity plus a second factor.
- **Host:** stays on the always-on PC. A movable host was discussed and not chosen.
- **Extension:** desktop Chrome and Edge only, for household members' computers. Each person creates a per-device API token in Baihe's settings (hash stored, shown once, revocable). The plan is to move the bridge from `page_server.py` (loopback, one shared token) into the API behind this auth. Built: the per-device tokens and their check ("Extension device tokens" in [`remote-access-permissions-accounts.md`](remote-access-permissions-accounts.md)). Not done yet: no bridge route in the API uses them, the bridge is still `page_server.py` on 8756, and the extension can't be pointed at another address. Never route port 8756.
- **Phones:** an installable PWA first. Capacitor is deferred. Mobile URL capture uses a share target (Android), an iOS Shortcut posting to the API, and pasting a URL into URL import. If a native wrapper is ever built, Google sign-in must open in the system browser.

## Repo work

1. Users table, allowlist, sessions, and the permission dependency plus its static test.
2. Google OIDC login and callback.
3. Per-device extension tokens (built), then move the extension bridge into the API (not done yet).
4. URL-import guards: http/https only, block private, loopback and link-local addresses (including after redirects), and caps on size, count and concurrency.
5. Per-user job limits, and per-user bandwidth caps for media. Built: each signed-in user may have 2 running and 5 queued jobs they started directly (`jobs/user_caps.py`, 429 beyond; a job started by another job, such as the speaker step a transcription starts when it ends, runs with no starter and is not counted) and 3 open audio/video streams (`api/routers/media_routes.py`, 429 beyond). Not built: a bandwidth (bytes per second) cap.
6. Verify Range and seek behaviour with a multi-GB file (the API uses `FileResponse`), and job progress through Caddy.
7. Set an upload size limit if uploads are ever allowed remotely (there is none today). Uploads, deletes and settings are PC-only unless the user decides otherwise.
8. PWA manifest and a minimal service worker (cache the app shell only), and check session cookies in installed PWAs on real devices.
9. Hardening: no public `/api/docs`, production mode only.
10. Operations: the PC never sleeps, Caddy and the API run as services on boot, an uptime alert, backups, dynamic DNS and certificate renewal monitoring, and per-device session lists with revocation.

## Accepted trade-offs

- A compromised household Google account gives access to that member's permissions. Sensitive permissions stay off by default.
- A Google outage blocks new logins; existing sessions keep working.
- The 24/7 PC exposes Baihe's own login page to the internet, and the user owns the patching.
- **OCR program path from the browser (`tesseract_cmd`): PC only (security review of PR #439, 2026-09-29).** The transcribe run, upload-and-transcribe and novel-OCR requests can name the OCR program the server runs (transcribe: `api/schemas/` `TranscribeRunRequest.tesseract_cmd` → `services/transcribe_service.py`; OCR chapter: `api/routers/novel_routes.py` form field → `services/novel_attach_service.py`; both end in `ocr.extract_text_tesseract`). Ocr-chapter is a local-only route; upload-and-transcribe (`media.upload + jobs.start` since 2026-10-21) applies the same refusal as the run route (`transcribe_routes.check_run_allowed`). The transcribe run route (`POST /api/transcribe/dramas/{id}/run`, `jobs.start`) refuses a request-supplied path with 403 unless the request comes from the PC itself (`api.auth.is_local_request`); remote runs use only the path saved in Settings, which is itself PC-only (the owner's accepted risk: the path stays editable in Settings at the PC). `ocr.extract_text_tesseract` sets pytesseract's command for one call under a lock and restores it after, so one run's path never stays set for later runs.
- **Import with lightnovel-crawler (Step 115b, 2026-09-30): PC only.** `GET /api/novel/lncrawl` (booleans only: installed, path set) and `POST /api/novel/dramas/{drama_id}/lncrawl` are `local_only()`. The job runs a program on the PC: the user-installed `lncrawl` (lightnovel-crawler, GPL-3.0, never imported or shipped by Baihe), found on PATH or at the PC-only Settings path `lncrawl_cmd`, which must name a file called lncrawl / lightnovel-crawler with no extension or `.exe` (a `.cmd`/`.bat` launcher is refused, on PATH too: Windows runs it through cmd.exe, which would treat `&`, `|` or `%` in the pasted URL as shell syntax). The argv is fixed (`lncrawl crawl --noin --format epub {--all | --first N | --last N} -- <url>`, no shell); the pasted URL must be http(s) with no userinfo or control characters and is checked with `url_guard` (private, loopback and link-local hosts refused) before the program starts. **lncrawl does its own fetching, DNS and redirects**, so Baihe's per-request SSRF pinning cannot cover what it fetches after that first check; that is why both routes stay PC-only rather than `sources.import`. The child gets the environment minus key/token/secret-looking variables and `BAIHE_*`, and a temp data folder inside the drama folder (removed afterwards); the run has a 90-minute timeout, a 20 MB cap on what it prints and a 1 GB cap on its data folder, and cancel or any cap kills the process tree (POSIX session; on Windows a Job Object with kill-on-close, plus `taskkill /T`). After a normal exit nothing is killed by PID (it may be reused); only if something lncrawl started still holds its output pipe is its process group (POSIX) or Job Object (Windows) ended. Stopping the API cancels every running import and kills its tree (`lncrawl_service.shutdown`, from the lifespan and `atexit`), and the startup sweep removes `.lncrawl_*` work folders older than any run can last. The child environment also drops `LNCRAWL_*` and `DATABASE_URL`, which would point lncrawl at a config or database outside its temp folder. What it printed is redacted (keys, tokens, paths, URL queries) and only a ≤480-character tail is stored, in the job result. The EPUB goes through `novel_attach_service`'s EPUB limits (50 MB, entry count, 100 MB unpacked, unsafe entries). Whether a site's terms allow a download is the user's call per title (the UI says so).
- Downloads come from the user's home IP.
- **Live capture residual risk (PR #589, 2026-10-06).** ffmpeg no longer opens any URL. `live_fetch.py` fetches the stream in Python and writes it to ffmpeg's stdin; ffmpeg runs with `-protocol_whitelist pipe -format_whitelist mpegts,mov,aac,mp3,flv,matroska,ogg,wav -i pipe:0`. The fetcher follows HLS itself (master playlist to the lowest-bandwidth variant or its audio rendition, the live media playlist by sequence number, AES-128 keys decrypted in Python, fMP4 init sections; byte ranges, SAMPLE-AES and other key formats are refused) and pipes any other response as is. Each of its requests, redirect hops included (at most 5), is http(s) only and goes through `services/egress_proxy.py` (target re-checked as public and pinned), with environment proxy settings ignored, TLS certificates verified, a 10 s connect timeout and a 20 s timeout on each read, and size caps on playlists, keys and segments, and at most 2000 entries per playlist. Each playlist, key or segment request, from connecting through the proxy's CONNECT answer, the TLS handshake and every redirect hop to the end of its body, must finish within 60 s (the stall timeout) or the capture ends as stalled; a timer shuts the request's sockets down when that time passes, so a host trickling its handshake, headers, body or chunked-encoding size and trailer lines cannot hold it longer. A stream that is not HLS is held to the same 60 s up to its first bytes, then piped as it arrives with no overall limit beyond the 20 s per read, the session's `max_minutes` and Stop. The proxy's own 30 s overall deadline on the upstream response head applies only to plain-http requests it forwards; a CONNECT tunnel (https) just pipes bytes, ended by the client's deadline above or after 120 s idle. Closing the proxy at the end of a session shuts down every connection it still has open; `StreamPump.halt()` shuts down its connections at any stage (TLS handshake, waiting for response headers, reading the body). yt-dlp's own requests use the same proxy. Tested with real ffmpeg 6.1.1 (`tests/test_egress_proxy.py`): a playlist variant, segment, key, audio rendition or init entry, or a redirect, naming `tcp://`, `httpproxy://`, `crypto+httpproxy://` or a private `http(s)://` address, a DASH `BaseURL` carrying `&#13;&#10;`, IMF and ffconcat files: a loopback listener receives no connection; a `file://` entry is never read. What ffmpeg can no longer do: the `tcp://` variant connect and the fixed `httpproxy://` CONNECT that the earlier design allowed. The format whitelist is not redundant: ffmpeg 6.1.1's DASH demuxer opens `http://` and `httpproxy://` fragment URLs even under `-protocol_whitelist pipe` (pinned by `test_piped_dash_is_refused_by_the_format_whitelist`; its HLS demuxer does respect it). For the same reason, live streams offered only as DASH (an MPD manifest) are deliberately no longer supported: the manifest reaches ffmpeg, which refuses it under the format whitelist, and the capture fails. What remains:
  - Any public host and port can be fetched from the home IP (except the Fetch standard's bad ports), for up to the session's `max_minutes`, one session at a time; a hostile server can send up to 64 MB per segment and 1 MB per playlist.
  - "Public" includes the home's own WAN address. A hostile stream can name it (or a DNS name that resolves to it), and on a router with NAT loopback (hairpin NAT) that connection reaches whatever the router forwards from the WAN to the LAN: the app's own public listener, and any other port-forwarded device or router page open on the WAN side.
  - The proxy's only authentication is its per-session random secret (now held only by the API process and yt-dlp, no longer in ffmpeg's environment).
  - A corporate or system HTTP(S) proxy, and a custom CA bundle from the environment, are not used for live capture.
  - yt-dlp extractors that start an outside program which fetches on its own bypass the proxy option: in yt-dlp 2026.8.19 the PhantomJS wrapper (douyutv, iqiyi, pornhub) runs `phantomjs` with no proxy flag, so with PhantomJS installed those pages are fetched unchecked. Not verified: whether the JS runtimes yt-dlp uses for YouTube (Deno, Node, Bun, QuickJS) can fetch on their own.
  - ffmpeg still parses hostile bytes, with the whitelisted demuxers only.
  - Condition for granting `media.import_url` to household users: all of (1) `tests/test_egress_proxy.py` passes with no skips against the ffmpeg installed on the PC (re-run after any ffmpeg upgrade, since the DASH behaviour above makes the format whitelist load-bearing). The capture tests are skipped without `ffmpeg` on PATH, and the https ones also need `openssl` on PATH, which Windows doesn't ship: Git for Windows has one in `C:\Program Files\Git\usr\bin`, so add that folder to PATH for the run, then run `python -m pytest -q -rs tests/test_egress_proxy.py` and check that the summary reports no skipped tests; (2) PhantomJS is not installed on the PC; (3) you accept that each such user can make the PC fetch from any public address as above. Starting live capture at the PC is unaffected.

## Unverified (not checkable from the session)

- Range support in the installed Starlette.
- Google's app-consent limits for an unverified app.
- The ISP's inbound-port policy and the home upload speed.
- Cloudflare's current terms, if that route is ever revisited.
- Mobile extension support, Web Share Target on iOS, and PWA push limits.
- Whether the app can use a separate capped key for household jobs, and what the monthly cap enforces.
- Sources fetches through a configured or environment proxy (B-25, `fix-b25-redirect-hops`): every hop's target is validated by name only and cannot be pinned, so a DNS answer that changes between the check and the proxy's own lookup is not caught.

## Rejected or deferred

Tailscale and other VPNs; Cloudflare Tunnel + Access (revisit if large media isn't needed remotely); Authelia and other self-hosted identity servers; per-person API keys (one exception since 2026-10-14: a member's own Ollama key for cloud models, see "Ollama cloud models" in [`remote-access-permissions-core.md`](remote-access-permissions-core.md)); remote key entry (same exception: a member pastes their own Ollama key from their device); a portable or dual host; a native mobile app.

## Effect on other docs and slices

- The Discover/Sources/Live spec's open question Q2 (what other devices may trigger) is answered by the permission list in the `remote-access-permissions-*.md` files: `media.import_url`, `sources.import`, `engines.paid`, `extension.send` and `media.stream` are off by default; browse, read, review, edit lines, and start and cancel jobs on media already on the PC are on. Slices S-3 to S-6 must not ship to non-local clients before the permission dependency (step 133) exists. Sign-in, proxy, pacing floors and cookies stay local-only. The saved yt-dlp cookies (Settings > Downloads) are used by the PC-only URL download and by a Live capture started at the PC (`is_local_request`); a Live start from another device never gets them.
- Live capture URLs (any public URL) map to `media.import_url`.
- History: option E (built-in logins, publicly exposed) was chosen on 2026-09-28, reversed the same day in favour of Tailscale, and is now chosen again on 2026-09-29 with the design above.
