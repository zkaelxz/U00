# Remote access decision (replaces D6: Tailscale)

Decided by the user on 2026-09-29, from a discussion session. No repo changes were made by that session; this file records the outcome.
It replaces D6 (Tailscale + Tailscale Serve) in [`migration-review.md`](archive/migration-review.md) and supersedes [`remote-access-design.md`](archive/remote-access-design.md).
**D5 stays** (admin actions are PC-only, on a separate loopback listener); built, see "D5: two listeners" below.

**Key entry (decided 2026-09-29):** the launcher (`start.bat`/`start.ps1`) sets `BAIHE_API_ALLOW_KEY_WRITES=1` unless the user already set it (an explicit `0` opts out), so API keys can be entered in the React Settings form at the PC, or by editing `.env`. Key writes stay `local_only()` and still require a direct loopback peer and Host, no proxy headers, and Origin, if sent, is loopback (`api/routers/settings_routes.py:_require_local_admin`); values are written to `.env` and never returned. `python -m api` started directly leaves the flag off.
Status: step 133 (users, sessions, permissions, static test) is built, see "Step 133" below; the step 134 sign-in backend (slice A1) is built on its branch, see "Step 134 backend" below; the rest is not. Implementation steps are proposed as 133-140 in [`baihe-roadmap-master.md`](archive/baihe-roadmap-master.md) section 5.

## Context

- The user doubted the VPN, so Tailscale is out.
- The PC is always on with a normal home IP. The user owns a domain.
- Household members use their own phones and computers, browser only.
- Today `api/server.py` has no authentication, and the API binds to loopback by default.

## Decided

- **Route:** Caddy on the PC with a real Baihe login. Household devices will stream and download large video; Cloudflare's request cap and its terms on large media are uncertain, and the extension behind Cloudflare Access is unproven.
- **Order of work:** build auth and permissions, test on the LAN through Caddy with a real certificate, and open the router port last.
- **Auth:** Google OIDC sign-in (a vetted library such as Authlib) plus a Baihe users allowlist. Match on Google's `sub`, require `email_verified`, use PKCE, state and nonce. Server-side sessions in a Secure, HttpOnly, SameSite cookie, with CSRF protection. Rate-limit login routes; audit-log sign-ins and admin actions. The first admin is granted locally with `python -m api grant-admin`, which also serves as recovery.
- **Permissions:** deny by default, one declared permission per route, and a static test that fails if a route has none.
  - Household scope: browse, read, review, edit lines, and start and cancel jobs on media already on the PC.
  - Separate permissions, off by default: `media.import_url` (yt-dlp), `sources.import` (manga and novel fetch), `engines.paid`, `extension.send`, `media.stream`.
- **Keys:** unchanged. Entered at the PC, resolved server-side, never sent to a device. Slice 24 stays off by default.
- **Admin:** stays on a separate loopback listener (D5) that Caddy never routes to. Remote admin, if ever wanted, would need identity plus a second factor.
- **Host:** stays on the always-on PC. A movable host was discussed and not chosen.
- **Extension:** desktop Chrome and Edge only, for household members' computers. Each person creates a per-device API token in Baihe's settings (hash stored, shown once, revocable). The plan is to move the bridge from `page_server.py` (loopback, one shared token) into the API behind this auth; not done yet: `extension.send` is defined but no route uses it, and the bridge is still `page_server.py` on 8756. Never route port 8756.
- **Phones:** an installable PWA first. Capacitor is deferred. Mobile URL capture uses a share target (Android), an iOS Shortcut posting to the API, and pasting a URL into URL import. If a native wrapper is ever built, Google sign-in must open in the system browser.

## Repo work

1. Users table, allowlist, sessions, and the permission dependency plus its static test.
2. Google OIDC login and callback.
3. Per-device extension tokens, then move the extension bridge into the API.
4. URL-import guards: http/https only, block private, loopback and link-local addresses (including after redirects), and caps on size, count and concurrency.
5. Per-user job limits, and per-user bandwidth caps for media.
6. Verify Range and seek behaviour with a multi-GB file (the API uses `FileResponse`), and job progress through Caddy.
7. Set an upload size limit if uploads are ever allowed remotely (there is none today). Uploads, deletes and settings are PC-only unless the user decides otherwise.
8. PWA manifest and a minimal service worker (cache the app shell only), and check session cookies in installed PWAs on real devices.
9. Hardening: no public `/api/docs`, production mode only.
10. Operations: the PC never sleeps, Caddy and the API run as services on boot, an uptime alert, backups, dynamic DNS and certificate renewal monitoring, and per-device session lists with revocation.

## Accepted trade-offs

- A compromised household Google account gives access to that member's permissions. Sensitive permissions stay off by default.
- A Google outage blocks new logins; existing sessions keep working.
- The 24/7 PC exposes Baihe's own login page to the internet, and the user owns the patching.
- **OCR program path from the browser (`tesseract_cmd`): PC only (security review of PR #439, 2026-09-29).** The transcribe run, upload-and-transcribe and novel-OCR requests can name the OCR program the server runs (transcribe: `api/schemas/` `TranscribeRunRequest.tesseract_cmd` → `services/transcribe_service.py`; OCR chapter: `api/routers/novel_routes.py` form field → `services/novel_attach_service.py`; both end in `ocr.extract_text_tesseract`). Upload-and-transcribe and ocr-chapter are local-only routes. The transcribe run route (`POST /api/transcribe/dramas/{id}/run`, `jobs.start`) refuses a request-supplied path with 403 unless the request comes from the PC itself (`api.auth.is_local_request`); remote runs use only the path saved in Settings, which is itself PC-only (the owner's accepted risk: the path stays editable in Settings at the PC). `ocr.extract_text_tesseract` sets pytesseract's command for one call under a lock and restores it after, so one run's path never stays set for later runs.
- **Import with lightnovel-crawler (Step 115b, 2026-09-30): PC only.** `GET /api/novel/lncrawl` (booleans only: installed, path set) and `POST /api/novel/dramas/{drama_id}/lncrawl` are `local_only()`. The job runs a program on the PC: the user-installed `lncrawl` (lightnovel-crawler, GPL-3.0, never imported or shipped by Baihe), found on PATH or at the PC-only Settings path `lncrawl_cmd`, which must name a file called lncrawl / lightnovel-crawler with no extension or `.exe` (a `.cmd`/`.bat` launcher is refused, on PATH too: Windows runs it through cmd.exe, which would treat `&`, `|` or `%` in the pasted URL as shell syntax). The argv is fixed (`lncrawl crawl --noin --format epub {--all | --first N | --last N} -- <url>`, no shell); the pasted URL must be http(s) with no userinfo or control characters and is checked with `url_guard` (private, loopback and link-local hosts refused) before the program starts. **lncrawl does its own fetching, DNS and redirects**, so Baihe's per-request SSRF pinning cannot cover what it fetches after that first check; that is why both routes stay PC-only rather than `sources.import`. The child gets the environment minus key/token/secret-looking variables and `BAIHE_*`, and a temp data folder inside the drama folder (removed afterwards); the run has a 90-minute timeout, a 20 MB cap on what it prints and a 1 GB cap on its data folder, and cancel or any cap kills the process tree (POSIX session; on Windows a Job Object with kill-on-close, plus `taskkill /T`). After a normal exit nothing is killed by PID (it may be reused); only if something lncrawl started still holds its output pipe is its process group (POSIX) or Job Object (Windows) ended. Stopping the API cancels every running import and kills its tree (`lncrawl_service.shutdown`, from the lifespan and `atexit`), and the startup sweep removes `.lncrawl_*` work folders older than any run can last. The child environment also drops `LNCRAWL_*` and `DATABASE_URL`, which would point lncrawl at a config or database outside its temp folder. What it printed is redacted (keys, tokens, paths, URL queries) and only a ≤480-character tail is stored, in the job result. The EPUB goes through `novel_attach_service`'s EPUB limits (50 MB, entry count, 100 MB unpacked, unsafe entries). Whether a site's terms allow a download is the user's call per title (the UI says so).
- Downloads come from the user's home IP.
- **Live capture residual risk (PR #589, 2026-10-06).** ffmpeg no longer opens any URL. `live_fetch.py` fetches the stream in Python and writes it to ffmpeg's stdin; ffmpeg runs with `-protocol_whitelist pipe -format_whitelist mpegts,mov,aac,mp3,flv,matroska,ogg,wav -i pipe:0`. The fetcher follows HLS itself (master playlist to the lowest-bandwidth variant or its audio rendition, the live media playlist by sequence number, AES-128 keys decrypted in Python, fMP4 init sections; byte ranges, SAMPLE-AES and other key formats are refused) and pipes any other response as is. Each of its requests, redirect hops included (at most 5), is http(s) only and goes through `services/egress_proxy.py` (target re-checked as public and pinned), with environment proxy settings ignored, TLS certificates verified, a 10 s connect timeout and a 20 s timeout on each read, and size caps on playlists, keys and segments, and at most 2000 entries per playlist. Each playlist, key or segment request, from connecting through the proxy's CONNECT answer, the TLS handshake and every redirect hop to the end of its body, must finish within 60 s (the stall timeout) or the capture ends as stalled; a timer shuts the request's sockets down when that time passes, so a host trickling its handshake, headers, body or chunked-encoding size and trailer lines cannot hold it longer. A stream that is not HLS is held to the same 60 s up to its first bytes, then piped as it arrives with no overall limit beyond the 20 s per read, the session's `max_minutes` and Stop. The proxy's own 30 s overall deadline on the upstream response head applies only to plain-http requests it forwards; a CONNECT tunnel (https) just pipes bytes, ended by the client's deadline above or after 120 s idle. Closing the proxy at the end of a session shuts down every connection it still has open; `StreamPump.halt()` shuts down its connections at any stage (TLS handshake, waiting for response headers, reading the body). yt-dlp's own requests use the same proxy. Tested with real ffmpeg 6.1.1 (`tests/test_egress_proxy.py`): a playlist variant, segment, key, audio rendition or init entry, or a redirect, naming `tcp://`, `httpproxy://`, `crypto+httpproxy://` or a private `http(s)://` address, a DASH `BaseURL` carrying `&#13;&#10;`, IMF and ffconcat files: a loopback listener receives no connection; a `file://` entry is never read. What ffmpeg can no longer do: the `tcp://` variant connect and the fixed `httpproxy://` CONNECT that the earlier design allowed. The format whitelist is not redundant: ffmpeg 6.1.1's DASH demuxer opens `http://` and `httpproxy://` fragment URLs even under `-protocol_whitelist pipe` (pinned by `test_piped_dash_is_refused_by_the_format_whitelist`; its HLS demuxer does respect it). For the same reason, live streams offered only as DASH (an MPD manifest) are deliberately no longer supported: the manifest reaches ffmpeg, which refuses it under the format whitelist, and the capture fails. What remains:
  - Any public host and port can be fetched from the home IP (except the Fetch standard's bad ports), for up to the session's `max_minutes`, one session at a time; a hostile server can send up to 64 MB per segment and 1 MB per playlist.
  - "Public" includes the home's own WAN address. A hostile stream can name it (or a DNS name that resolves to it), and on a router with NAT loopback (hairpin NAT) that connection reaches whatever the router forwards from the WAN to the LAN: the app's own public listener, and any other port-forwarded device or router page open on the WAN side.
  - The proxy's only authentication is its per-session random secret (now held only by the API process and yt-dlp, no longer in ffmpeg's environment).
  - A corporate or system HTTP(S) proxy, and a custom CA bundle from the environment, are not used for live capture.
  - yt-dlp extractors that start an outside program which fetches on its own bypass the proxy option: in yt-dlp 2026.8.19 the PhantomJS wrapper (douyutv, iqiyi, pornhub) runs `phantomjs` with no proxy flag, so with PhantomJS installed those pages are fetched unchecked. Not verified: whether the JS runtimes yt-dlp uses for YouTube (Deno, Node, Bun, QuickJS) can fetch on their own.
  - ffmpeg still parses hostile bytes, with the whitelisted demuxers only.
  - Condition for granting `media.import_url` to household users: all of (1) `tests/test_egress_proxy.py` passes with no skips against the ffmpeg installed on the PC (re-run after any ffmpeg upgrade, since the DASH behaviour above makes the format whitelist load-bearing). The capture tests are skipped without `ffmpeg` on PATH, and the https ones also need `openssl` on PATH, which Windows doesn't ship: Git for Windows has one in `C:\Program Files\Git\usr\bin`, so add that folder to PATH for the run, then run `python -m pytest -q -rs tests/test_egress_proxy.py` and check that the summary reports no skipped tests; (2) PhantomJS is not installed on the PC; (3) you accept that each such user can make the PC fetch from any public address as above. Starting live capture at the PC is unaffected.

## Step 133: permission model as built

`BAIHE_API_AUTH=off` (default) keeps today's behaviour for the owner at the PC: every request is the local owner with every permission, no session, no CSRF. Because of that, off mode serves only direct loopback requests: `LoopbackOnlyGate` answers a generic 403 to any request with a non-loopback peer, Host or Origin, or with any proxy/forwarding header (`X-Forwarded-*`, `Forwarded`, `Via`, `X-Real-IP`, ...), on every path including `/api/health` and the frontend (a proxied health check must not report a server it would refuse to serve). A non-loopback `BAIHE_API_HOST` is also refused at startup (`python -m api` and `create_app`); the env check alone could not stop a same-PC reverse proxy or `uvicorn --host`, the request-time gate does. The gate also blocks DNS rebinding (the Host is the attacker's name). `on` enforces the rules below. Catalogue (`services/auth_service.py`): household defaults `library.read`, `lines.read`, `lines.edit`, `jobs.start`, `jobs.cancel`, `review.use`; off by default `media.import_url`, `sources.import`, `engines.paid`, `extension.send`, `media.stream`; admin-only (from the `is_admin` flag, never grantable) `admin.library`, `admin.settings`, `admin.diagnostics`, `admin.users.read`, `admin.users`. Each admin permission is classified view or write (`ADMIN_VIEW_PERMISSIONS` / `ADMIN_WRITE_PERMISSIONS`; unlisted counts as write, and `tests/test_api_household_listener.py` fails on an unclassified one): view is `admin.users.read` only; `admin.library`, `admin.settings` and `admin.diagnostics` mix reads with writes, so they are write as a whole. `local_only()` means a direct loopback request at the PC (no proxy headers, loopback Host/Origin), with no session needed; it is how "uploads, deletes and settings are PC-only" is enforced; on the D5 household listener (below) it refuses every request. In both modes a POST/PUT/PATCH to a `local_only()` route must also be `application/json` or carry `X-Baihe-Local: 1`, so a page on another loopback port cannot reach it with a no-cors "simple" request (text/plain, form-urlencoded or multipart); With auth off the same rule covers every `/api` POST/PUT/PATCH, not just `local_only()` routes: off mode has no CSRF token and the Origin check ignores the port, so otherwise a page on another loopback port (a dev server, say) could start a paid LLM run or cancel a job with a bodyless POST. With auth on, every non-GET already needs the session's CSRF header (a custom header, so it forces a preflight), and the rule stays scoped to `local_only()` routes. DELETE and GET are unaffected. The React client (`postJson`, `deleteJson`, `postMultipart`) sends `X-Baihe-Local: 1` on every mutating request. `LocalOnlyCrossSiteGate` applies this before the request body is read. The Origin port is still not compared with the API's own; the content-type/header rule makes that unnecessary for mutations. `tests/test_api_permissions.py` fails if any route lacks exactly one declaration.

The route -> permission table (one row per declaration, with every method and path) is in [`route-permissions.md`](route-permissions.md); `tests/test_api_permissions.py` fails when it drifts from the app.

- **Uploads and deletes are `local_only()`** (media upload, upload-and-transcribe, the yt-dlp URL download `POST /api/media/dramas/{id}/download-url` (until redirect-validated URL guards and per-user job/bandwidth caps exist, repo-work items 4 and 5; then `media.import_url`) (it runs yt-dlp with every default extractor except `generic`, and fetches a plain direct media link itself with every redirect hop re-validated, pinned and byte/time-capped; what remains is that yt-dlp's site-specific extractors still do their own redirects and DNS without our guard, which is why the route stays PC-only), novel attach-text/epub/OCR, `DELETE /api/dramas/{id}`, discover title delete, `DELETE /api/translate/history`, and the PC-only deletes: remove audio/video, remove raw novel text, delete a translation version, series character, preset or voice-bank entry, and the learned-style reset `POST /api/review-extras/dramas/{id}/style/reset`, which wipes a series-wide or library-wide learned profile, and its undo `POST /api/review-extras/dramas/{id}/style/restore`, which brings back one of the last `db.STYLE_HISTORY_KEEP` (5) profiles a learn or reset replaced), per repo-work item 7. - **Source domain lists** (sources that move between domains, e.g. xbanxia and ToonKor): every `/api/source-domains*` route is `local_only()`, reads included. The list decides where source requests go, so setting it from another device would be the same SSRF/exfiltration pivot as the proxy URL. The list and proposals return **host names** with a port only when it isn't 443 (`toonkor1.org`, `toonkor1.org:8443`), a deliberate, PC-only exception to "no fetched URLs": the owner has to see what a proposal would switch to before confirming it. Never a scheme, path or query. Which hosts are contacted: the listed domains, plus any redirect target the ordinary transport follows from them (every hop public-address checked, Cookie/Authorization dropped on a host change). A result that ended on an unlisted host, or moved from https to http, is never used as content or cached under the listed URL; that domain counts as failed. ## D5: two listeners (as built)

`python -m api` serves two FastAPI apps from one process (two uvicorn servers in one event loop), so both see the same in-memory job list (`background_jobs`), the authority for running jobs:

- **Admin listener**, `127.0.0.1:BAIHE_API_PORT` (8600): exactly today's behaviour. It is what `start.bat`, `start.ps1` and the installed launcher open. Auth off (every request is the local owner), `LoopbackOnlyGate` refuses anything that isn't a direct loopback request (proxy headers, public Host, non-loopback Origin or peer), `/api/docs` and `/api/openapi.json` are served, and its lifespan runs the background services and their shutdown work (GPU-queue poller, model re-evaluation, lightnovel-crawler kill). `check_bind_safety` is unchanged for it.
- **Household listener**, `127.0.0.1:BAIHE_API_HOUSEHOLD_PORT` (unset by default: no second listener, and nothing changes for anyone who doesn't set it; suggested value 8610, since start.bat and the launcher suggest 8601 as a fallback admin port). Built by `create_app(settings, listener="household")` from the admin settings (`api_config.household_settings`): sign-in always on, no background services and none of their shutdown work in its lifespan, no docs or schema (401 without a session, 404 with one), engine-key writes off. Nothing on it is ever "the PC": `api.auth.is_local_request` is False and `local_only()` refuses every request (the early gate before the body is read, and the dependency itself), so a loopback request with the proxy's forwarding headers stripped still can't reach a PC-only route or a handler's own PC check (the Tesseract path on transcribe runs, glossary overwrite, the library-wide learned style, key/endpoint writes via `_require_local_admin`, path values in `GET /api/settings`, `/api/meta` `local`, `/api/auth/me` `zone`). An admin account signed in there keeps the household permissions and the admin view permissions (`admin.users.read`: the user list and the audit log) but no admin write permission, and it loses the admin override (`admin_override`, set from `is_admin` by `resolve_session` and cleared here): it still sees every item and job (`ownership_service._sees_everything`), but changes only what a member of its own account could, meaning items it owns or that are shared (`_may_override`; a 403 names the PC otherwise). So from away an admin can't flip another member's private flag (nor flip a series holding a PC drama), can't edit another member's private drama or series (every non-GET route with a `{drama_id}`/`{series_id}` path, plus series assignment and bulk translate by id), and can't cancel or stop a job a member couldn't see (another user's or the PC's non-drama jobs, and jobs on dramas it can't edit). All of this comes from `api.auth.listener_principal`, applied to every session check, the event stream's re-check and `/api/auth/me`'s permission list; default-deny: an `admin.*` permission not listed as view is dropped, and an admin principal without the override flag acts as a member. admin changes are PC-only (D5, user decision 2026-09-30 "block only writes"), and a remote admin session has no second factor. `admin.library`, `admin.settings` and `admin.diagnostics` mix reads with writes, so none of their routes is served there. Its uvicorn access log is off, since those lines carry query strings such as the sign-in callback's code.
- **Checked at startup** (`api_config.check_household_bind_safety`, run by `python -m api` and `create_app`). `python -m api` refuses to start (exits with the error) only for `BAIHE_API_AUTH=on` or a non-loopback host next to a household port. Every other failure below, and an invalid `BAIHE_PUBLIC_URL` (which is ignored, so sign-in counts as not configured), skips only the household listener with a warning naming the setting in the console and app log; the PC's own listener always starts so a typo in `.env` can't lock the owner out, and Diagnostics' remote-health says `BAIHE_PUBLIC_URL` is invalid when that is the reason. `create_app` refuses all of them. The conditions: a household port equal to the admin port or to the extension bridge's 8756 (`page_server.DEFAULT_PORT`), a non-loopback host (both listeners use `BAIHE_API_HOST`, which must then be loopback), `BAIHE_API_AUTH=on` (the admin listener must stay the loopback-only off mode; with auth on there, a proxy pointed at 8600 would get signed-in access to it) `BAIHE_API_ENV=development` (the dev server is one auto-reloading app) and sign-in not configured or an invalid public URL (any of `BAIHE_GOOGLE_CLIENT_ID`, `BAIHE_GOOGLE_CLIENT_SECRET`, `BAIHE_PUBLIC_URL` missing). No port beyond loopback is opened by default.
- **Stopping:** when either server stops (a failed start such as a port already in use, Ctrl+C, the launcher's clean-stop route through `shutdown_service.register_stopper`), both stop, then the usual clean stop runs once. Signals are handled once for both servers, not by each uvicorn server. With the household port unset, `python -m api` runs the single server exactly as before. Once a clean stop has begun (the launcher's stop route, the console-close handler, Ctrl+C), `background_jobs` refuses every new job start with a 409 ("Baihe is stopping..."), on both listeners, so a signed-in household member can't start a job during the grace wait that the process exit would then kill mid-write. The refusal is set before the stop takes its list of jobs to cancel, so a start racing the stop is either cancelled or refused.
- **Own-port guards:** the Jellyfin server address, the SearXNG base URL and a local ntfy topic may never point at one of Baihe's own loopback ports; `BAIHE_API_HOUSEHOLD_PORT`, when set, is one of them, like `BAIHE_API_PORT` and 8756.
- **Migrating from single-port sign-in.** The household port is unset by default, and leaving it unset changes nothing. Anyone who today signs in on the single port (`BAIHE_API_AUTH=on`, a proxy pointed at 8600) must migrate before setting it, because startup refuses the combination:
  1. Set `BAIHE_API_AUTH=off`. It now applies only to the admin listener on 8600, the PC's own window, which then serves direct loopback requests only.
  2. Set `BAIHE_API_HOUSEHOLD_PORT=8610` (any free loopback port other than the admin port and 8756; the installer's `enable-remote` also refuses 8600 and 8601, and the service's own port).
  3. Point the reverse proxy (Caddy) at the household port, `reverse_proxy 127.0.0.1:8610`, never at 8600.
  4. Configure Google sign-in (`BAIHE_GOOGLE_CLIENT_ID`, `BAIHE_GOOGLE_CLIENT_SECRET`, `BAIHE_PUBLIC_URL`) as before; it is used by the household listener, where sign-in is always on.
  5. Startup exits with an error only if `BAIHE_API_AUTH=on` for the admin listener or `BAIHE_API_HOST` is non-loopback next to a household port; the error names the setting to change. Every other problem (including development mode, `BAIHE_API_ENV=development`) skips only the household listener with a warning.
  6. Rollback: unset `BAIHE_API_HOUSEHOLD_PORT` (and point the proxy back, or turn sign-in back on for the single port as before).

  Nothing here opens a router port; forwarding a port from the router to the proxy remains a step only the user takes.

  The single-port sign-in setup (`BAIHE_API_AUTH=on`, household port unset) is still accepted, but `python -m api` warns about it at every start, on the console and in the app log (so Diagnostics' log tail shows it too; `api_config.single_port_sign_in_warning`): "Sign-in is on for the single port (BAIHE_API_AUTH=on, no BAIHE_API_HOUSEHOLD_PORT). PC-only actions are only fully protected with the two-port setup: behind a reverse proxy this port tells the PC from other devices by request headers alone. Migrate with the steps under "Migrating from single-port sign-in" in docs/remote-access-decision.md." It is a warning, not a refusal. To silence it, migrate with the steps above; with `BAIHE_API_AUTH=off` (the default) there is no warning.
- **Hardening (WP2).** The household app answers only requests whose `Host` is `BAIHE_PUBLIC_URL`'s name and port (case, one trailing dot and the scheme's default port don't matter; IPv6 literals compared in normal form; a non-ASCII name must be written in its punycode `xn--` form, the one browsers send, and startup refuses it otherwise, since Python's IDNA 2003 codec maps some letters, such as `ß`, differently from browsers). Any other Host, a missing or repeated one, or one with userinfo or a path is a 400 (`invalid_host`) before routing, on every path including `/api/health`, so a DNS-rebinding page or another name pointed at the proxy reaches nothing; `X-Forwarded-Host` is ignored, so the proxy must pass the browser's Host on (Caddy does by default). The admin listener is unchanged: loopback Hosts only, through `LoopbackOnlyGate`. Every household reply, the other gates' 400/401/403 included, carries `Content-Security-Policy` (`default-src 'self'`, `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, `connect-src 'self'`; `frame-src` limited to `https://www.youtube-nocookie.com` and `https://player.twitch.tv` for the Live page's stream video; `data:`/`blob:` for images and media; `'unsafe-inline'` for scripts and styles because the Reader's sandboxed srcdoc page inherits the policy and runs inline scripts), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: same-origin` and a `Permissions-Policy` that turns off camera, microphone, geolocation, payment and USB; a header a route sets itself (the stricter CSP on cover and review images) is kept. `Strict-Transport-Security: max-age=31536000` is added only when the request's scheme is https and there is exactly one `X-Forwarded-Proto: https` (the proxy on this PC saw https). The peer isn't checked: uvicorn's proxy headers handling (pinned to `forwarded_allow_ips=127.0.0.1` for both listeners) has already replaced it with the browser's address, and it takes the scheme from `X-Forwarded-Proto` only for a loopback peer. Unexpected-error 500 replies are written outside the middleware and carry no headers or page content. The household listener is not started (warning, PC listener unaffected) unless `BAIHE_GOOGLE_CLIENT_ID`, `BAIHE_GOOGLE_CLIENT_SECRET` and `BAIHE_PUBLIC_URL` are all set (the message names them, never their values). `GET /api/meta` leaves `environment` empty on the household listener. Session cookies are unchanged: `__Host-` names, Secure, `Path=/`, no Domain; the session cookie HttpOnly and SameSite=Lax, the CSRF cookie readable and SameSite=Strict.
- Per-device sessions are built, see "Signed-in devices" below.

Step 134 backend (slice A1) as built: Google OIDC authorization code flow with PKCE (S256), `state` and `nonce` in a single-use, 10-minute, in-memory login transaction (`services/oidc_service.py`); the `id_token` is verified against Google's JWKS (RS256 only; cached, re-fetched on an unknown `kid` at most once a minute) for `iss`, `aud`, `exp`, `iat`, nonce, and `email_verified` must be literally `true`. A returning user is matched by `sub`; a user with no binding yet is bound on first login by an allowlisted verified email; anything else (not allowlisted, email bound to another `sub`, inactive) is refused with a generic `/?login_error=not_allowed` and an audit row naming the email. Every login issues a fresh session and revokes the one the client presented. Cookies: `__Host-baihe_session` (HttpOnly, SameSite=Lax), `__Host-baihe_csrf` (readable, SameSite=Strict; the React client echoes it as `X-CSRF-Token`, which the server checks against the session's stored hash) and `__Host-baihe_oidc` (the pending transaction); plain names only for plain-http loopback dev with `BAIHE_API_COOKIE_SECURE=0`. A failed CSRF check is 403 with code `csrf_failed` (a missing permission stays `forbidden`). Rate limits key on the rightmost `X-Forwarded-For` entry only when the TCP peer is loopback (Caddy), otherwise on the peer (uvicorn's default `proxy_headers` with `forwarded_allow_ips=127.0.0.1` already rewrites `request.client` to that same entry behind Caddy, so the result is the same either way). The bucket is the IPv4 address or the IPv6 /64 (IPv4-mapped IPv6 counts as IPv4); login and callback are each capped per bucket (20), per IPv6 /56 (40) and per IPv4 /24 or IPv6 /48 (200), all per 10 minutes, finest tier first (a request refused by one tier isn't charged to the wider ones). There is no global cap: a caller's callbacks are live for the transactions it started itself, so a global cap could be exhausted by ten /64s (A1-M1). Pending transactions are capped per bucket (20) and overall (1000); when full, the IPv4 /24 or IPv6 /48 holding the most is picked and its busiest bucket loses its oldest, so a flood spread one transaction per /64 evicts itself, not other users' transactions. Stored/audited addresses are coarsened to IPv4 /24 or IPv6 /48. `/me`'s `zone` is `"pc"` for a direct loopback request and `"internet"` otherwise until the network-zones slice adds `"lan"`. Settings: `BAIHE_GOOGLE_CLIENT_ID`, `BAIHE_GOOGLE_CLIENT_SECRET`, `BAIHE_PUBLIC_URL` (environment or `.env`); missing -> login 503 and `sign_in_configured: false`; a non-https public URL other than localhost is refused at startup. Allowlist from the PC: `python -m api add-user <email>`, `deactivate <email>`, `grant <email> <permission>`.

Requirements carried to step 134 (login), all met by slice A1 above:
- Issue a fresh session from `auth_service.create_session` on every successful login and revoke the client's previous session; never adopt a session id the client sent (session fixation).
- Name the cookie with the `__Host-` prefix (`__Host-baihe_session`: Secure, `Path=/`, no `Domain`) so a sibling subdomain can't plant or overwrite it; keep the loopback-http dev relaxation working (a `__Host-` cookie requires Secure, so dev without TLS needs the plain name).
- Rate-limit the login and callback routes per client address with `SlidingWindowRateLimiter` and audit-log sign-ins.
- Expired sessions are deleted when presented, and at every start of the admin listener with background services on (`auth_service.sweep_stale_sessions`, from the API lifespan): sessions past their absolute or idle expiry and those of a deactivated user go, with their CSRF hashes. Login transactions live in memory only, so a restart leaves none.

## Ownership and sharing (auth slices B1 and B2) as built

B1 (`services/ownership_service.py`, #414) added `owner_user_id`/`is_private` on dramas and series, the visibility rule (auth off, the local owner and admins see everything; otherwise a series is visible to its owner or when it is not private, and a drama to its series' owner, else not if its series is private, else to its owner or when it is not private) and the share-by-default setting. B2 (branch `auth-b2-ownership-enforcement`, 2026-09-29) enforces it at the API. A denied item is always a 404, identical to a missing one.

- **Path guard.** `require_permission` runs `api.auth.require_path_visible` after the permission check: any `{drama_id}` or `{series_id}` path parameter the caller can't see is a 404. One central check covers every such route (159 at the time) and every new one. Child ids under those paths (lines, terms, notes, history, versions, pages, characters, clip candidates, bulk jobs) were audited and are already scoped to the parent by their services. `local_only()` routes are the local owner and see everything. Editing is visibility-based (user decision 1), so reads and writes share the guard. `tests/test_api_ownership.py` has the static half (every owned route has a guarded declaration; any other path parameter must be nested under one or be listed in `OWNERSHIP_EXEMPT_PARAMS` with a reason) and a route walk: user B gets 404 on every drama/series route for user A's private drama and for a drama in A's private series.
- **Disk usage (`/api/data-usage`).** All nine routes (scan a folder of the app's data folder, move one item into Baihe's Trash folder, move the automatic-backup folder, list the Trash, restore from it, permanently delete one Trash item, empty the Trash, list unused voice clips, move unused voice clips to Trash) are `local_only()`: they read, move and delete files on the PC, and Caddy refuses `/api/data-usage*` too (the `@pc_only` matcher). Paths in requests and responses are relative to the data folder (never absolute, never the data folder's own path); the only absolute path is the move `destination` the owner types, which is not echoed back. The path guard has no id to check, so `services/disk_usage_service.py` validates every path: no `..`, absolute path, drive letter or `:`, trailing dot or space, and every component must exist as an ordinary file or folder (a symlink or junction anywhere on the way is refused, never followed; a link inside a scanned folder is counted as itself, not entered). Server-enforced protection for clear and move: the data folder itself, the live SQLite files (`-wal`, `-shm`, `-journal` too), `.env` and key files, the INSTALLED/PORTABLE markers, saved site sign-ins, installer files, anything in the program folder, the Trash folder, and any folder holding one of those. Both refuse (409) while any background job, restore or maintenance run holds the library, and while the GPU lock has a live holder: the CLI writes no `job_records` rows, so a CLI run is detected only while it holds the GPU lock (its GPU steps). Known limit: a CLI run of non-GPU steps leaves no trace and is not detected. Clear and move also refuse when the data folder is a drive root, the user's home, a folder holding it or a shell folder (Documents, Desktop, ...), for a folder that couldn't be read fully (paths of MAX_PATH or longer and names ending in a dot or space count as unreadable) or that holds a link, and for top-level entries Baihe doesn't create (shown, protected as "Not created by Baihe"). Items that can't be recreated (a title's media, saved voice samples and benchmark cases, `library/source_profiles`, `saved_comics`, and every backup copy under `library/backups`) also need `confirm_irreplaceable`. Clear needs `confirm=true` plus the size and file count the user saw (409 when the item changed) and does not delete anything: it renames the item, atomically and on the same volume, into `<data folder>/baihe_trash/<id>/payload` and writes a `manifest.json` beside it (original relative path, kind, size, file count, time); it refuses when the item is on another volume or the new path would reach MAX_PATH, and never copies. The Windows Recycle Bin is not used: the installed API runs as a service account, so its bin is not the owner's. `GET /trash` takes no lock shared with the scan. Restore renames the payload back to its original relative path under the exclusive hold, only when every folder on the way still exists with no link, the place is free, it would pass the clear protection checks, and no job runs (409 with a plain reason otherwise). The only permanent deletes in the feature are `trash/purge` (one entry; needs the typed word `DELETE` exactly and the size shown, 409 when it changed; the size is `null` only when the list showed it as unknown because the walk limit was reached) and `trash/empty` (needs `DELETE` plus `expected_item_count` and `expected_size_bytes` of the list shown, both required, 409 `changed` when they differ or the Trash is too large to measure completely): they act only on folders directly inside `baihe_trash` whose names match the id pattern (`YYYYMMDD-HHMMSS-<8 hex>`), refuse the Trash root or an entry that is a link or reparse point, run under the exclusive hold, delete with a walk that unlinks links without following them (on POSIX relative to open folders, so a folder swapped for a link after it was listed can't redirect a delete; on Windows path by path with a check before each step, a residual window that needs write access to the Trash folder) and removes folders bottom-up (clearing a read-only bit only on ordinary files and folders, never through a link), and on any failure keep what is left in Trash and return a generic error with no paths. Move works only for the automatic-backup folder (through `auto_backup_service.set_settings`, which moves the copies and saves the setting together); the destination must be an existing real folder outside the data and program folders. The scan is a bounded read-only walk (2,000,000 entries or 30 s, then `partial=true`) run in the thread pool. Unused voice clips (`GET /unused-voice-clips`, `POST /unused-voice-clips/to-trash`) offer only files named `clone_ref_*` or `clone_pick_*` directly inside a title's `voice_refs/` (voice-bank copies are written to the title's root folder, so they are not offered) that no `characters.ref_audio_filename` of that title matches (by last name part, ignoring case) and no live speaker-merge undo record holds (a hook that is empty until those records exist), for a title with no running dub, narration or audiobook job. A response carries the title, file type, size and date plus an opaque id (an HMAC of title id and file name under a key made at process start): no file name or path, and an id from another title or an earlier run matches nothing. Moving needs `confirm=true` and each clip's shown size, then looks every id up again under the exclusive hold, checks it is still unreferenced and unused by a job right before the rename and once more right after it (putting it back, without overwriting anything already there, if a speaker picked it in between), all under that title's clip lock, which clip upload, remove and choose also take around their file check and database write, and uses the same Trash rename, so it can be restored. A clip that changed is skipped, not an error; a batch that stops part-way (library busy, Trash move failed) returns the error with `details.moved_count`, `moved_bytes` and `skipped` for what was already moved, and the request takes at most 500 clips (the UI sends larger selections in batches). This route deliberately needs only `confirm=true` and the shown sizes, not `confirm_irreplaceable`: the files go to the restorable Trash and a permanent delete still needs the typed word `DELETE`. There is no automatic expiry of Trash.
- **Backups (Step 43, redefined 2026-09-29).** Every `/api/backups/*` route (auto-backup settings, back up now, the rotating copies' info and a copy's dramas, restore one drama, delete one copy or all) is `local_only()`: backups and restores are PC-only. None takes a path parameter; the drama to restore is a body field (`drama_id`, an id inside the copy, not a live drama), so the path guard has nothing to check. A copy is chosen by its file name (`snapshot`, a query or body field), which the service only matches against the backup folder's own listing of copy files and never uses as a path; responses name copies by file name, never by path. Restore and delete need `confirm=true` plus the typed word (RESTORE, DELETE); deleting every copy also needs an explicit `all=true`, and a delete naming neither a copy nor `all` is refused. `all=true` deletes only the copies this library manages (its id in the manifest and recorded as written by it); a copy it doesn't manage (another library's in a shared folder, a hand-copied library's with the same id, an untagged or unreadable one) is deleted only with `include_unmanaged=true`, by name or with `all`. With no copy named, the dramas list and the restore answer 409 with `details.reason = "choose_copy"` and the candidate copies (name, created_at, sequence, size, managed: names only, no paths) when the newest copy can't be told for sure. The snapshot never holds `.env` or keys (they live outside the library, and the backup writer skips any `.env`), and the snapshot folder is inside `backups/`, which every backup excludes. `POST /api/backups/import/list` and `POST /api/backups/import` take an uploaded backup file (a snapshot copy, a manual backup zip or a bare `library.db`) and are also `local_only()`: the upload's Content-Length is checked against `BAIHE_MAX_UPLOAD_MB` before any of the body is read (chunked bodies are refused) and the body stream itself is counted; the file's database is read only from ordinary tables, under a time limit; the import needs `confirm=true` plus `RESTORE` and is refused while a backup, export, restore or cleanup runs. Every imported drama is new, owned by the acting user and private per their sharing default (never taken from the file); a stored file name (audio, cover, pages and the like) is kept only when it names a file inside the new drama's own folder and that drama's files came with the import, otherwise it is cleared; responses carry ids, titles and counts, no paths.
- **Lists.** Library `/dramas`, `/stats`, `/recent`, `/costs`, `/series`, `/search` (line text) and `/history` show only visible dramas (`db.drama_visible_sql`, the SQL twin of the rule, shared with `db.list_dramas`). Stats and spend count only visible dramas; spend not logged against a drama is left out for household users. Translate history is per user: a household user sees their own rows; rows with no user (the PC, the extension) are for admins and the local owner. `POST /api/translate` now stamps the user.
- **Drama ids in bodies.** Bulk translate reports a drama the caller can't see as `not_found`, like a missing one. Source chapter and URL imports and tracking a series into a drama 404 on one the caller can't see.
- **New items.** `drama_service.create_drama` (API create, Discover import-to-library) stamps `new_item_defaults`: the creator, private unless they share by default. Sharing by default is off unless the person turns it on (user decision 2026-09-30): the local owner's household setting and a user with no stored value both mean private, and a new user starts with it off. Existing accounts were switched to private once by `init_db` (their stored 1 came from the old column default, which nobody could change); a choice made after that is kept (marker `migrations.share_by_default_off`), and existing items keep their flags. Items created at the PC or with sign-in off have no owner and are stored private, so once sign-in is on the household sees them only after an admin shares them (Settings > Sharing notes this and can filter to them). New series were already stamped by `get_or_create_series_for`. The CLI creates none.
- **Jobs.** With auth on, `ActingPrincipalMiddleware` gives each request a holder that `require_permission` fills, and `background_jobs.start_job`/`start_process_job` record that user as the job's owner (memory and `job_records.owner_user_id`). A job started outside a request (the CLI, a job's own threads) is the PC's. `ownership_service.can_see_job`: admins, the local owner and auth off see every job; otherwise a `<prefix><drama_id>` job (`background_jobs.DRAMA_JOB_PREFIXES`) follows its drama's visibility, for its starter too (a drama that goes private stops showing them its jobs), and any other job is visible only to its starter. `/api/jobs` lists only those; GET and cancel of any other are 404. The fixed-id results (Discover bulk-extract and navigation-help, Sources search, URL preview, series and import jobs) and Live sessions (list, status, stop) use the same rule, except that a fixed-id result nobody may see answers 200 with status `idle`, the same as when nothing has run (a Sources import into a drama the caller can't see stays 404, like the drama). The per-drama auto-tune and glossary-extraction status reads answer `idle` too when no run is held.

- **Central guard instead of a per-route dependency.** The spec's option 1 (plan section B, enforcement point 1). It needs no change per route and covers new routes by default; the static test fails if a route names a drama or series under another parameter name.
- **Cancel follows visibility, not "starter or admin only".** The spec suggested starter-only cancel. That would change who holds `jobs.cancel` today (anyone who can see a shared drama can stop its translate run), so cancel uses the same visibility rule as reading a job. Revisit if household members should not stop each other's runs.

The owner check means nobody reads another user's result. Per-user job ids would remove the wait; not done, to keep the change small.
- **Tracking a series** still relies on the process's latest `sources_series_<source>` result, whoever loaded it. It reveals nothing new to the caller (they name the series), so it isn't owner-checked.
- **Push (SSE, `GET /api/events`, `library.read`, user decision 2026-09-30 "SSE everywhere"):** one stream per tab carries job changes, the bell list and Live status, with the permission of the three GET routes it replaces (`/api/jobs`, `/api/notifications`, `/api/live/sessions`). With auth on the session is re-checked at most every 5 s (before a batch or heartbeat), without counting as activity (`resolve_session(touch=False)`), and the client closes the stream while its tab is hidden, so an open tab never keeps an idle session alive; sign-out or a revoked `library.read` ends the stream. One process-wide sweep of `job_records` (a few columns, every 5 s while any stream is open) catches jobs other processes run. Live events carry status only (`cues: []`); cue text still comes from the GET. Caps: 6 streams per user (or the local owner), 32 in total (429 beyond, the client polls instead); per stream at most 64 pending ids, then one `resync`; a stream closes after 30 minutes and the client reconnects. A `ping` event after 15 s of silence (the client treats about 45 s of silence as a dropped stream), `Cache-Control: no-cache`, `X-Accel-Buffering: no` (Caddy/nginx). EventSource sends the session cookie and no custom header; a GET needs no CSRF token. Keys, paths and other users' data never appear (the same projections as the GET routes).

Clip files: no merge, undo, rename or Characters-field edit deletes a clip file from `voice_refs/`, whatever its kind (upload `clone_ref_`, pick copy `clone_pick_`, voice-bank copy), since removing files is PC-only (`local_only()`). Choosing a candidate still replaces the speaker's own previous `clone_pick_` copy for good, as before (never an upload). A clip left behind, including a merged-away speaker's pick or upload, is listed and removed by the PC owner from the Disk usage view (restorable Trash). A clip that a live undo record (unexpired, not retired) would give back counts as in use there (`db.live_speaker_merge_undo_clips`). Expiry and retirement of undo records touch database rows only; a merge retires earlier undos for either speaker inside its own transaction, and the bookkeeping after a commit is best-effort and never changes the response. The request needs `confirm=true`.
- **Household-wide by decision (plan B, point 6):** voice bank, presets, Discover known titles, tracked sources and notifications. The header bell list (`GET /api/notifications`, `library.read`, Step 44 item 5) follows the same split: its new-chapter events are household-wide, and a job-ended event is listed only to a caller who can see that job (`ownership_service.can_see_job`, as `/api/jobs`); it carries no job id, path or line text. Event ids are millisecond timestamps, not a counter, so a gap says nothing about hidden events; 500 events are kept so other users' jobs don't push a viewer's own out of their 50. A Discord/ntfy push (the PC owner's channel, which the household may share) names a drama only when a household member could see it: a private drama's (or private series') title is left out (security review, 2026-09-30). `GET /api/sources/tracked` lists every tracked series, but a linked drama the caller can't see is reported as `drama_id: null`.
- **Monthly spend is household-wide.** The translate config's `month_spend` (and the monthly cap checked before a run) is the whole library's spend this month, not the caller's: the cap is one household budget. It is a single total, so it names no drama; the per-drama cost lists are filtered (Lists above).
- **Queued GPU jobs don't say what they're waiting for** (review M-1). The message used to name the running job ("GPU busy with Ollama translation (<title>)"), which leaked another user's private drama title to anyone who could see the waiting job, and was mirrored to `job_records`.
