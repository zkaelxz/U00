# Remote access: permission model as built, part 2

These notes were written as one file. "Above" and "below" in them can mean another part: the decision, the three permission parts, [`remote-access-listeners.md`](remote-access-listeners.md) and [`remote-access-ownership.md`](remote-access-ownership.md) are listed in [`remote-access-decision.md`](remote-access-decision.md), and [`threat-model.md`](threat-model.md) and [`household-access.md`](household-access.md) summarise them.

- **Sources tools and the Discover pasted listing** (branch `parity-b7a-sources-tools`, 2026-09-29): "Will this site work?" (`POST /api/sources/url/preflight`, job `sources_url_preflight`), identify media (`POST /api/sources/url/identify-media`, job `sources_url_identify`), and the pasted-page-source preview and novel import after a verification page (`POST /api/sources/url/preview-pasted`, `/url/import-pasted`) are `sources.import`, like the URL preview and import: a pasted URL is checked with `url_guard` in the request, the fetch goes through the same paced, byte- and deadline-capped pasted-URL SourceClient, and from another device it is static HTTP only; the pasted routes fetch nothing (user-assisted tier). Page source pasted from another device chooses both the URL's domain and the page, so its import keeps nothing but the text: no site profile is saved or offered, no profile use or failure is recorded, no AI result is cached and the source's capability record is not updated (`adaptive.import_novel(remember=False)`, `generic_import.fetch_page(record=False)`); at the PC it keeps the profile and caches as usual. Only an identify run started at the PC keeps the full resource URLs. The pasted preview parses one page at a time (409), and the regexes it runs stop at the next "<", so hostile markup stays linear. Pasted bodies are capped by Content-Length and a counted body stream (413) and then by the models (422: 5 MB of page source, 200,000 characters of listing text); the pasted text is parsed only and never returned. Identify media returns scheme+host+path only; a picked resource's full address (a signed CDN link can carry a token) comes only from `GET /api/sources/url/identify-media/resource`, which is `local_only()` like the video download it feeds. The pasted-URL diagnostics list `GET /api/sources/url/extractions` is `admin.settings`, like the attempt log and profiles. The Discover pasted listing `POST /api/discover/bulk-extract/pasted` fetches nothing but runs an AI engine: `jobs.start` plus `require_engines_allowed`, and it shares the `discover_bulk_extract` job (its result route is `library.read`, its commit `admin.library`, as before).
- **Pasted-URL extraction (Sources parity SO09, SO06, SO10, `parity-b7b-sources-extraction`):** the AI fallback on the novel URL import is opt-in per request (`use_ai`, `engine`); the handler checks the engine name (reference-capable engines only, 422 otherwise) and calls `require_engines_allowed` for it before any job starts, so a paid engine needs `engines.paid` and a remote caller without it can still use Ollama. The key is resolved on the PC from .env and stays in the engine object; `GET /api/sources/url/ai-engines` (`sources.import`) returns engine names and the saved default only, no key and no key status. The comic import (`POST /api/sources/url/import-comic`, SO06) is `sources.import` like the novel one: same public-address check in the request, static HTTP only for a request not from this PC, the same opt-in AI fallback, and it only adds pages to a manhua/manga/manhwa drama (append-only `pipeline.add_page_images`, the per-drama `sourceimport_<id>` job). Its image downloads go through the same paced client (every redirect hop re-validated) under the shared page-upload rules (`services/page_import_limits.py`, user decision 2026-09-29): at most 30 MB per image, 300 download attempts and 1 GB per import; a response must be `image/*` or a generic binary type, and its header (read without decoding) must show PNG, JPEG or WebP at no more than 100 megapixels; an accepted image is then decoded once (EXIF orientation applied, a strip taller than 3x its width cut into pages). Anything else is skipped with a reason and listed, never stored; the same rules apply to a reviewed import. A run from another device reads the site's shared "seen on other chapters" image memory (so repeating banners are still dropped) but does not add to it. One comic import (a pasted-URL comic import or a reviewed comic import) runs at a time in the process (409 otherwise), and its pages are prepared and written one image at a time with each download dropped once written, so memory holds at most one import's download budget plus one image's prepared pages; an open comic review keeps its images on disk under `<library>/source_review_tmp/`, removed on expiry, replacement or once its import ends (a failed write removes the partial folder; folders older than the review expiry are swept, so another process's live reviews are left alone). A damaged image that passes the header checks but fails to decode, rotate or re-encode is skipped, not fatal. Review extraction (SO10) lives under `/api/sources/dramas/{drama_id}/extraction` so the path guard hides a drama the caller can't see: reading the review, re-running it with corrections, its image thumbnails (raster types Pillow read, `nosniff`, `sandbox` CSP, `no-store`) and importing it (the same append-only writes in the per-drama `sourceimport_<id>` job) are `sources.import`, like the import that opened it. Re-running fetches nothing: it reads the page the import job already kept (in memory, one review per drama, at most 4, 30 minutes), and every correction is an option the review offered, named by id or offered selector, never free CSS or text. **Judgement call:** saving the corrections as the site's profile and approving a suggested profile are `local_only()`: a site profile changes how every later import from that domain is read, which is a settings-like write, and settings writes are PC-only (profile rollback stays `admin.settings`). Follow-ups from the branch's security review: an image that failed to download or that Pillow couldn't read can't be marked as a page in a review (422); a URL import started from another device never auto-saves a HIGH-confidence generated profile (it is held for approval at the PC, `ExtractionReport.hold_profiles`); a review of a page read through the saved signed-in browser answers 404 away from the PC; shown URLs blank signed path segments (as for the AI prompt); import and profile save re-check the revision under the review lock. Accepted for now: reviews are capped at 4 process-wide (not per user), and each comic review can keep up to the 1 GB import budget on disk for 30 minutes (a review closes when its import starts); the AI fallback is not counted against the monthly spend cap (one call per page, cached).
- **Sources:** tracking a series and dismissing a new-chapter notification are `sources.import`; listing sources, tracked series and notifications is `library.read`; searching the sources and listing one series' chapters (spec S-3, paced jobs that fetch from this PC but write nothing) are `library.read` too, per the spec's "read and search allowed". A series listing from a request not from this PC runs with the adapter's `allow_browser` off, so an adapter that renders its series page (Fanjiao, Step 113) refuses instead of opening a browser. A series result can also carry download links (and their public extraction codes) that a work's own page posts, e.g. an EPUB on Baidu Pan or Lanzou (Step 115, lightnovel.fun): shown to the person to open themselves, scheme+host+path only, never fetched by the app. Importing chapters (S-4, `POST /api/sources/{name}/import`, a per-drama job that re-fetches the chapter list and takes chapter ids only) is `sources.import`, and so is saving a comic series' chapters as CBZ files into the PC's `saved_comics` folder (`POST /api/sources/{name}/save`, the same ids-only re-fetch, one save at a time, no path in the result; turning on `POST /api/sources/tracked/save-cbz` makes the chapter check save a tracked comic series' new chapters the same way), and so is reading which chapters of a series are already in a drama or were left failed or not attempted (`GET /api/sources/{name}/import-state`, Step 107: sources.db only, fetches nothing, the drama is checked with the same `can_edit_drama` as the import); tracking a new series needs this process's loaded series result so its chapters are recorded as known. The paste-a-URL preview and novel-text import (S-5, `POST /api/sources/url/preview|import`) are `sources.import` too: the URL is checked with `url_guard` in the request, and a request not from this PC gets static HTTP only (no signed-in profile, no browser). "Check now" for tracked series (S-7, `POST /api/sources/check-now`, the same `sources_chapter_check` job the API's scheduler starts) and pointing a tracked series' auto-import at a drama (`POST /api/sources/tracked/drama`, fetches nothing) are `sources.import` too. A "Check now" from a request not from this PC runs with each adapter's `allow_browser` off, so a browser-only source (Fanjiao, Step 113) reports an error for that series instead of opening a browser; the scheduled check runs on the PC. Sign-in (S-6: open a window on the PC, forget the saved profile), the per-tier "Test now" (a browser on the PC) and the proxy URL are `local_only()`; the sign-in and tier-test job results are answered by `GET /api/sources/jobs/{job_id}/result` only to a request from this PC (404 otherwise), and their status, description, message and scrubbed error show in `GET /api/jobs` (`library.read`) only to a caller `ownership_service.can_see_job` lets see them: a job started at the PC is hidden from household members and shown to admins, and a tier test's outcome is saved in the source's capability record (`GET /api/sources/{name}`). Site settings (the Manage sources page) stay `local_only()` for writes: "editable on the LAN, never from the internet" needs the network-zones slice, since today a request is either `pc` or `internet`.
- **Bug reports ("Report a problem"):** sending one is `library.read`, so a household tester can report from the device where the problem happened; the server-side section it adds (git commit, setup summary, redacted log tail) is stored with the report but returned only to a caller holding `admin.diagnostics`, so the log stays admin-only. A text-only report is `library.read` from anywhere, but uploads are PC-only: the optional screenshot is accepted only on a direct loopback request (with auth off every request already is one), and a remote report that includes one is refused with a 403 and a plain message rather than having the image silently dropped; the React dialog hides the screenshot field off the PC. The body is capped at the stream itself (a request with `Transfer-Encoding` is refused, and more body bytes than the cap end in a 413 whatever `Content-Length` says), and each principal may send 5 reports per 10 minutes (429). The GitHub issue link the dialog builds uses only the server-scrubbed texts and never the server section, which stays in the saved report and in Copy report. Reports sent from away from the PC are capped at 10 per user and 100 in all, and every report counts toward 250 MB; past a cap, sending is a 409. Reports sent at the PC count against neither number cap, so remote members can't lock the owner out. Listing and reading reports are `admin.diagnostics`; deleting one is `local_only()` with `confirm=true` and the report's folder stamp from the list, and report ids are never reused.
- **Maintenance assistant (Step 42):** every `/api/assistant/*` route is `local_only()`, reads included: the assistant reads the app's code, read-only git output, the redacted log, job history and the support report, so none of it is reachable from another device even by an admin. Asking and the changelog also need Developer Mode on (409). Its tools are a fixed read-only table (no file, git-write, settings or library tool exists; an invented tool name is answered "no such tool"); paths stay inside the repo and never reach `library/`, `.git`, virtualenvs, dotfiles or secret-named files, and in a git checkout only tracked files are readable; git and pytest run with fixed argument lists, a timeout, literal pathspecs and no shell; the one test run per question gets a throwaway library, an empty .env and no key-looking environment variables; tool output, answers and backlog text have keys, tokens and this PC's folder prefixes removed. One question at a time (409), and the monthly spending cap applies. The engine key is resolved server-side, never from the request. The default engine is Ollama (on this PC); a cloud engine (Claude, DeepSeek, Gemini), or Ollama whose endpoint is not loopback, is refused with 409 (`details.reason` `cloud_consent_required`) until the owner saves a per-provider "send code and logs to this provider" consent (`cloud_consent` on `POST /api/assistant/settings`, shown in Settings > Developer Mode and on the Assistant page), because the tools send source code and redacted logs to the engine and a prompt-injected log line could steer which files are read. Step 60's optional review role (off by default) adds no route: it runs on the saved review engine, which must be a different provider from the answering engine, with the same read-only tools (the one test run per question is shared with it), and its verdict is shown next to the fix without changing or hiding it. The review engine is held to the same consent rule as the answering engine: without that provider's saved consent a cloud reviewer, or Ollama at a non-loopback address, is never called (checked server-side; the review comes back "unavailable" with the reason and the fix is still shown). Escalation is user-triggered: the saved tier ladder (`tiers` on `POST /api/assistant/settings`; default Ollama, then Gemini if its key is set, then one paid hosted engine with a key; engines with no key are skipped, and settings expose keys only as `engine_keys` booleans) is shown on the page, and `POST /api/assistant/ask` with `escalate: true` must name a tier of that ladder and, for a tier that leaves this PC, carry `consent: true` on that very request (409 `escalation_consent_required` otherwise) on top of the saved per-provider consent above; nothing escalates on its own, and a failed tier (no key, Ollama not running, a 429) comes back as an error naming the next tier without calling it. An escalation carries the question, the recent chat (redacted server-side) and the previous tier's redacted tool output (`evidence`, at most 16,000 characters, redacted again on receipt). `POST /api/assistant/report` (Developer Mode) returns the chat, that tool output and the Diagnostics support report as one redacted text for the user to copy; it uploads nothing. A proposed fix is returned as patch text only. `{backlog_id}` (a backlog row) is app-wide and PC-only.
- **Maintenance assistant GitHub delivery (Step 72):** every `/api/assistant/github*` route is `local_only()`. Off by default: until it is enabled with a repo and a token, no route makes any GitHub call. The token is a key: stored in `.env` as `BAIHE_GITHUB_TOKEN` through the same writer as engine keys, behind the same key-write gate (`BAIHE_API_ALLOW_KEY_WRITES=1`, `confirm=true`), sent only as an `Authorization` header to the fixed host `api.github.com` (repo paths only, no redirects, a timeout), never returned, and scrubbed from every error. Preview makes no network call and returns the exact diff and a sha256 over that diff, the repo and the base; deliver needs `confirm=true` plus that sha256 (a RED `publish_to_shared_target` action), creates one new `baihe-assistant/...` branch and one draft PR into the configured base (default `baihe-subtitler`), and has no code path that updates or deletes an existing ref. The patch is applied in Python against the base branch's current files and refused if any hunk doesn't match; paths are plain repo-relative (no `..`, absolute or `.git` paths) and may not touch anything that runs before review: `.github/` (CI workflows run with the repo's CI token) and `.claude/` (the SessionStart hook) at any depth; `CLAUDE.md` and `CLAUDE.local.md` at any depth (they steer any Claude Code session on the branch); config that python, pytest, tox, npm or PostCSS load from the working directory, at any depth (`conftest.py`, `sitecustomize.py`, `usercustomize.py`, `pytest.ini`, `.pytest.ini`, `tox.ini`, `setup.cfg`, `pyproject.toml`, `.npmrc`, `postcss.config.*`, `.postcssrc*`); at the repo root `run_tests.py`, `check_setup.py`, `start.bat`, `.mcp.json`, `requirements*.txt` and `constraints*.txt`; and directly under `frontend/` `package.json`, `package-lock.json`, `.oxlintrc.json`, `tsconfig*.json`, `{vite,vitest,playwright,eslint}.config.*`, plus everything under `frontend/scripts/`. All are compared case-insensitively; a hunk whose content only matches more than 20 lines from its `@@` line is refused, as is any hunk line with a bidi-control or zero-width character, and binary, mode, rename or copy changes and any stray line outside the hunks are refused so what is shown is what is delivered. A failed PR open leaves the new branch (named in the error); the app never deletes a ref.
- **Benchmark Lab (Step 38):** reads (options, cases, golden sets, run records, one run's results, the Model Arena view) and `POST /api/benchmark/estimate` (a body-taking read that spends nothing) are `admin.diagnostics`, like the rest of Diagnostics. Adding, importing and deleting cases, "add as regression test" from a line, and starting a run are `local_only()`: a run can call paid engines on the owner's keys, needs `confirm=true` (the page shows the estimate first), is refused when the monthly cap is used up or the estimate is over what is left, stops at the cap while running, and logs its spend to `usage_log`. Import reads only pasted JSONL/TSV (2 MB, 500 cases); nothing is downloaded. Keys are resolved server-side and never returned; stored errors are redacted. `{case_id}` and `{run_id}` are household-wide admin records (`OWNERSHIP_EXEMPT_PARAMS`).
- **Model deprecation assistant (Step 40):** `GET /api/models/status` is `admin.diagnostics` and reads only the shipped registry and the cached last check (no call out). `POST /api/models/check` is `local_only()`: it sends the owner's keys (headers only) to three fixed model-list URLs (Anthropic, Google, DeepSeek) with a timeout, at most once a minute (429), and caches only model ids plus a redacted error. `POST /api/models/presets/{preset_id}/switch` is `local_only()` with `confirm=true`: it changes one preset's model to one its engine offers, only if the preset still has the model the user saw (409 otherwise). Nothing switches automatically. `POST /api/models/overrides` and `POST /api/models/overrides/clear` are `local_only()` with `confirm=true`: they set or clear the user's own replacement for a built-in default or workflow-tier model (stored as app settings; 409 if the model changed since the user looked); saved presets are not touched.
- **Setup readiness (B11):** `GET /api/setup/readiness` is `library.read`, so a household member sees which optional packages are installed, `gpu_found`, `torch_cuda`, `ffmpeg`/`ffmpeg_libass`, a JavaScript runtime, whether the Tesseract program exists, and whether Ollama answers and has its default model, plus presence booleans for the engine keys and the Hugging Face token. The key and token booleans are already visible in `GET /api/settings`; the package, GPU and program flags are new member-visible facts about the PC, accepted so a disabled control can say why. Booleans only: the response model has no string, path, version or URL field, and nothing in the request reaches a probe (the Ollama address is the saved setting). Installing stays `local_only()` plus `admin.diagnostics`.
- **Model downloads are PC-only (owner decision 2026-10-12).** A run started away from the PC (`api.auth.is_at_pc` false) is refused with 403 `model_not_downloaded` before any job starts when a model it would load is not on disk: transcribe run and Transcribe queue items, autotune, re-transcribe one or many lines, compare transcription, re-time and align-to-audio resplit (Qwen3 aligner), speaker detection, dub, Scanlate run (OCR, the ML bubble detector when picked), fix-flagged hearing, SenseVoice tags and Live. `services/model_readiness_service.py` builds each run's model list and reads only the local caches. Such a run then loads offline (`lib/model_offline.py`): a child process gets the Hugging Face offline switches in its own environment, a server thread loads with `local_files_only` (Qwen3, Whisper, PaddleOCR-VL, the bubble detector, Scanlate's LaMa, also for re-render and export) or from the cache folder (manga-ocr, SenseVoice), vocal separation does not fall back to an undownloaded Demucs, and speaker detection does not fall back to pyannote 3.1, so a newer upstream revision is not fetched either. The owner downloads a model by running the feature once at the PC; once it is on disk a member can run it.
- **Model re-evaluation (Step 40b):** the overview, decision history and `POST /api/models/reeval/estimate` (spends nothing) are `admin.diagnostics`. Schedule settings, candidates (add / reject / reopen), "Run now" (`confirm=true`) and promotion (`confirm=true`) are `local_only()`. A run is an ordinary Benchmark Lab run (same estimate refusal and `benchmark_lab` job; the monthly cap applies when one is set). The schedule is off by default and can be turned on only while a monthly cap above $0 is set in Settings or a per-run limit (`max_cost_usd`) is set; saving an enabled schedule returns its current estimate. The API's hourly background check starts a run only when the schedule is on, a candidate is open, one interval has passed since the schedule was turned on (or since the last run or attempt), and no other job is running or queued and no restore or maintenance hold is active; if neither limit is set any more (the cap was cleared later) and the run would cost anything, it skips without recording an attempt. Candidates are model strings the user adds; nothing browses provider catalogs or downloads models. Promotion is the only call that changes the production record or Settings' default engine; nothing is promoted by running. `{model_candidate_id}` is a household-wide admin record (`OWNERSHIP_EXEMPT_PARAMS`).
- **Job queue** (`/api/queue`, `services/queue_service.py`, owner request 2026-10-10): every route is `jobs.start`, as the owner asked. Adding an item needs the title to be the caller's own and, for Translate on a paid engine, `engines.paid`; a member sees and changes only items for their own titles, at most 50 each. Start, pause, the start time and the stop-on-failure policy are refused (403) in the service to anyone but the PC owner (auth off, the local owner, or an admin with the override, i.e. on the admin listener), not `local_only()`, so the owner's own admin session can run it; a household-listener admin has no override and is refused. Each item starts as its adder, with permissions re-read when it starts, through the stage's own start function, so the cap, `lines.edit` for an overwrite and ownership apply as for a click. Paid Translate items are skipped unless a monthly cap above $0 is set (as for scheduled model re-evaluation), and before each one the cap and the estimate are checked. A document from another process (a restart or a restored backup) is settled on read: running items become interrupted, the queue stops and a passed start time is "missed"; nothing resumes on its own.
- **Remote-access health** (`GET /api/diagnostics/remote-health`, `services/remote_health_service.py`): `admin.diagnostics` like the other Diagnostics reads, so it is served only on the PC's admin listener (the household listener drops `admin.diagnostics`, and Caddy's `@pc_only` refuses `/api/diagnostics/*`); the React banner also asks only when the page is on the PC. It returns the last scheduled result only: states, whole days left, Unix times and fixed messages, never the public name, an address, the check URL or a path; reading it starts no check. The check runs from `api/background.py` only while an https `BAIHE_PUBLIC_URL` and `BAIHE_API_HOUSEHOLD_PORT` are both set (otherwise no thread and no outbound call): a TLS handshake with Caddy on 127.0.0.1 for the public name (chain and name verified; warn under 14 days left, critical under 5, expired or untrusted), a TCP connect to the household listener, and, only when `BAIHE_REMOTE_IP_CHECK_URL` is set in `.env` (kept there like the notification URLs, never in app_settings or a response), an https read of this PC's public IP (timeout, no redirects, pinned public address, 64 bytes) compared with the public name's DNS answer (both lookups bounded to 5 s; with no address of the same family it is "unknown", never an alert). Alerts go to the bell and, under the "remote" category, Discord/ntfy once when a problem starts or gets worse and once when it clears; a cycle that can't read the last saved result neither alerts nor saves, a failing save can't cause a repeat alert, and a cycle has a 45 s deadline and gives up (writing and sending nothing) as soon as the monitor is stopped. Admin > Remote access sets that address without editing `.env`: `GET /api/diagnostics/remote-health/ip-check` (`configured` only), set and clear (`POST .../ip-check`, `.../ip-check/clear`: `local_only()` plus the key-write gate and `confirm=true`, like the notification URLs; https only, no user info, at most 512 characters, every address public via `url_guard`, written under the one fixed name) and Test (`POST .../ip-check/test`, `local_only()`: one check now, one at a time and at most every 5 s, a state and a fixed message back, nothing saved or alerted). None returns the address; the running monitor re-reads `.env` each cycle, so no restart is needed.
- **Ports panel** (`GET /api/diagnostics/ports`, `services/settings_service.baihe_ports`): `local_only()`, PC only. Port numbers, an active flag and fixed how-to-change text; never a path, URL or secret.
