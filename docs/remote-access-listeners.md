# Remote access: two listeners

These notes were written as one file. "Above" and "below" in them can mean another part: the decision, the three permission parts, [`remote-access-listeners.md`](remote-access-listeners.md) and [`remote-access-ownership.md`](remote-access-ownership.md) are listed in [`remote-access-decision.md`](remote-access-decision.md), and [`threat-model.md`](threat-model.md) and [`household-access.md`](household-access.md) summarise them.

## D5: two listeners (as built)

`python -m api` serves two FastAPI apps from one process (two uvicorn servers in one event loop), so both see the same in-memory job list (`background_jobs`), the authority for running jobs:

- **Admin listener**, `127.0.0.1:BAIHE_API_PORT` (8600): exactly today's behaviour. It is what `start.bat` and the installed launcher open. Auth off (every request is the local owner), `LoopbackOnlyGate` refuses anything that isn't a direct loopback request (proxy headers, public Host, non-loopback Origin or peer), `/api/docs` and `/api/openapi.json` are served, and its lifespan runs the background services and their shutdown work (GPU-queue poller, model re-evaluation, lightnovel-crawler kill). `check_bind_safety` is unchanged for it.
- **Household listener**, `127.0.0.1:BAIHE_API_HOUSEHOLD_PORT` (unset by default: no second listener, and nothing changes for anyone who doesn't set it; suggested value 8610, since start.bat and the launcher suggest 8601 as a fallback admin port). Built by `create_app(settings, listener="household")` from the admin settings (`api_config.household_settings`): sign-in always on, no background services and none of their shutdown work in its lifespan, no docs or schema (401 without a session, 404 with one), engine-key writes off. Nothing on it is ever "the PC": `api.auth.is_local_request` is False and `local_only()` refuses every request (the early gate before the body is read, and the dependency itself), so a loopback request with the proxy's forwarding headers stripped still can't reach a PC-only route or a handler's own PC check (the Tesseract path on transcribe runs, glossary overwrite, the library-wide learned style, key/endpoint writes via `_require_local_admin`, path values in `GET /api/settings`, `/api/meta` `local`, `/api/auth/me` `zone`). An admin account signed in there keeps the household permissions and the admin view permissions (`admin.users.read`: the user list and the audit log) but no admin write permission, and it loses the admin override (`admin_override`, set from `is_admin` by `resolve_session` and cleared here): it still sees every item and job (`ownership_service._sees_everything`), but changes only what a member of its own account could, meaning items it owns or that are shared, plus items made at the PC (no account owner), which count as the admin's own work so a job can be started on them from away (owner decision 2026-10-18, `ownership_service._owns`; the private flag itself still changes only at the PC) (`may_override`; a 403 names the PC otherwise). So from away an admin can't flip another member's private flag (nor flip a series holding a PC drama), can't edit another member's private drama or series (every non-GET route with a `{drama_id}`/`{series_id}` path, plus series assignment and bulk translate by id). The one exception is jobs: an admin there may cancel or force-stop anyone's job, so a runaway job can be stopped from away (owner decision 2026-10-12, `ownership_service.may_cancel_job`); deleting job history stays PC-only (`local_only()`). All of this comes from `api.auth.listener_principal`, applied to every session check, the event stream's re-check and `/api/auth/me`'s permission list; default-deny: an `admin.*` permission not listed as view is dropped, and an admin principal without the override flag acts as a member. admin changes are PC-only (D5, user decision 2026-09-30 "block only writes"), and a remote admin session has no second factor. `admin.library`, `admin.settings` and `admin.diagnostics` mix reads with writes, so none of their routes is served there. Its uvicorn access log is off, since those lines carry query strings such as the sign-in callback's code.
- **Checked at startup** (`api_config.check_household_bind_safety`, run by `python -m api` and `create_app`). `python -m api` refuses to start (exits with the error) only for `BAIHE_API_AUTH=on` or a non-loopback host next to a household port. Every other failure below, and an invalid `BAIHE_PUBLIC_URL` (which is ignored, so sign-in counts as not configured), skips only the household listener with a warning naming the setting in the console and app log; the PC's own listener always starts so a typo in `.env` can't lock the owner out, and Diagnostics' remote-health says `BAIHE_PUBLIC_URL` is invalid when that is the reason. `create_app` refuses all of them. The conditions: a household port equal to the admin port or to the extension bridge's 8756 (`page_server.DEFAULT_PORT`), a non-loopback host (both listeners use `BAIHE_API_HOST`, which must then be loopback), `BAIHE_API_AUTH=on` (the admin listener must stay the loopback-only off mode; with auth on there, a proxy pointed at 8600 would get signed-in access to it) `BAIHE_API_ENV=development` (the dev server is one auto-reloading app) and sign-in not configured or an invalid public URL (any of `BAIHE_GOOGLE_CLIENT_ID`, `BAIHE_GOOGLE_CLIENT_SECRET`, `BAIHE_PUBLIC_URL` missing). No port beyond loopback is opened by default.
- **Stopping:** when either server stops (a failed start such as a port already in use, Ctrl+C, the launcher's clean-stop route through `shutdown_service.register_stopper`), both stop, then the usual clean stop runs once. Signals are handled once for both servers, not by each uvicorn server. With the household port unset, `python -m api` runs the single server exactly as before. Once a clean stop has begun (the launcher's stop route, the console-close handler, Ctrl+C), `background_jobs` refuses every new job start with a 409 ("Baihe is stopping..."), on both listeners, so a signed-in household member can't start a job during the grace wait that the process exit would then kill mid-write. The refusal is set before the stop takes its list of jobs to cancel, so a start racing the stop is either cancelled or refused.
- **Own-port guards:** the Jellyfin server address, the SearXNG base URL and a local ntfy topic may never point at one of Baihe's own loopback ports; `BAIHE_API_HOUSEHOLD_PORT`, when set, is one of them, like `BAIHE_API_PORT` and 8756.
- **Migrating from single-port sign-in.** The household port is unset by default, and leaving it unset changes nothing. Anyone who today signs in on the single port (`BAIHE_API_AUTH=on`, a proxy pointed at 8600) must migrate before setting it, because startup refuses the combination:
  1. Set `BAIHE_API_AUTH=off`. It now applies only to the admin listener on 8600, the PC's own window, which then serves direct loopback requests only.
  2. Set `BAIHE_API_HOUSEHOLD_PORT=8610` (any free loopback port other than the admin port and 8756; the installer's `enable-remote` also refuses 8600 and 8601, and the service's own port).
  3. Point the reverse proxy (Caddy) at the household port, `reverse_proxy 127.0.0.1:8610`, never at 8600.
  4. Configure Google sign-in (`BAIHE_GOOGLE_CLIENT_ID`, `BAIHE_GOOGLE_CLIENT_SECRET`, `BAIHE_PUBLIC_URL`) as before; it is used by the household listener, where sign-in is always on.
  5. Startup exits with an error only if `BAIHE_API_AUTH=on` for the admin listener or `BAIHE_API_HOST` is non-loopback next to a household port; the error names the setting to change. Every other problem (including development mode, `BAIHE_API_ENV=development`) skips only the household listener with a warning.
  6. Rollback: unset `BAIHE_API_HOUSEHOLD_PORT` (and point the proxy back, or turn sign-in back on for the single port as before).

  Nothing here opens a router port; forwarding a port from the router to the proxy remains a step only the user takes.

  The single-port sign-in setup (`BAIHE_API_AUTH=on`, household port unset) is still accepted, but `python -m api` warns about it at every start, on the console and in the app log (so Diagnostics' log tail shows it too; `api_config.single_port_sign_in_warning`): "Sign-in is on for the single port (BAIHE_API_AUTH=on, no BAIHE_API_HOUSEHOLD_PORT). PC-only actions are only fully protected with the two-port setup: behind a reverse proxy this port tells the PC from other devices by request headers alone. Migrate with the steps under "Migrating from single-port sign-in" in docs/remote-access-decision.md." It is a warning, not a refusal. To silence it, migrate with the steps above; with `BAIHE_API_AUTH=off` (the default) there is no warning.
- **Hardening (WP2).** The household app answers only requests whose `Host` is `BAIHE_PUBLIC_URL`'s name and port (case, one trailing dot and the scheme's default port don't matter; IPv6 literals compared in normal form; a non-ASCII name must be written in its punycode `xn--` form, the one browsers send, and startup refuses it otherwise, since Python's IDNA 2003 codec maps some letters, such as `ß`, differently from browsers). Any other Host, a missing or repeated one, or one with userinfo or a path is a 400 (`invalid_host`) before routing, on every path including `/api/health`, so a DNS-rebinding page or another name pointed at the proxy reaches nothing; `X-Forwarded-Host` is ignored, so the proxy must pass the browser's Host on (Caddy does by default). The admin listener is unchanged: loopback Hosts only, through `LoopbackOnlyGate`. Every household reply, the other gates' 400/401/403 included, carries `Content-Security-Policy` (`default-src 'self'`, `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, `connect-src 'self'`; `frame-src` limited to `https://www.youtube-nocookie.com` and `https://player.twitch.tv` for the Live page's stream video; `data:`/`blob:` for images and media; `'unsafe-inline'` for scripts and styles because the Reader's sandboxed srcdoc page inherits the policy and runs inline scripts), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: same-origin` and a `Permissions-Policy` that turns off camera, microphone, geolocation, payment and USB; a header a route sets itself (the stricter CSP on cover and review images) is kept. `Strict-Transport-Security: max-age=31536000` is added only when the request's scheme is https and there is exactly one `X-Forwarded-Proto: https` (the proxy on this PC saw https). The peer isn't checked: uvicorn's proxy headers handling (pinned to `forwarded_allow_ips=127.0.0.1` for both listeners) has already replaced it with the browser's address, and it takes the scheme from `X-Forwarded-Proto` only for a loopback peer. Unexpected-error 500 replies are written outside the middleware and carry no headers or page content. The household listener is not started (warning, PC listener unaffected) unless `BAIHE_GOOGLE_CLIENT_ID`, `BAIHE_GOOGLE_CLIENT_SECRET` and `BAIHE_PUBLIC_URL` are all set (the message names them, never their values). `GET /api/meta` leaves `environment` empty on the household listener. Session cookies are unchanged: `__Host-` names, Secure, `Path=/`, no Domain; the session cookie HttpOnly and SameSite=Lax, the CSRF cookie readable and SameSite=Strict.
- Per-device sessions are built, see "Signed-in devices" in [`remote-access-permissions-accounts.md`](remote-access-permissions-accounts.md).

Step 134 backend (slice A1) as built: Google OIDC authorization code flow with PKCE (S256), `state` and `nonce` in a single-use, 10-minute, in-memory login transaction (`services/oidc_service.py`); the `id_token` is verified against Google's JWKS (RS256 only; cached, re-fetched on an unknown `kid` at most once a minute) for `iss`, `aud`, `exp`, `iat`, nonce, and `email_verified` must be literally `true`. A returning user is matched by `sub`; a user with no binding yet is bound on first login by an allowlisted verified email; anything else (not allowlisted, email bound to another `sub`, inactive) is refused with a generic `/?login_error=not_allowed` and an audit row naming the email. Every login issues a fresh session and revokes the one the client presented. Cookies: `__Host-baihe_session` (HttpOnly, SameSite=Lax), `__Host-baihe_csrf` (readable, SameSite=Strict; the React client echoes it as `X-CSRF-Token`, which the server checks against the session's stored hash) and `__Host-baihe_oidc` (the pending transaction); plain names only for plain-http loopback dev with `BAIHE_API_COOKIE_SECURE=0`. A failed CSRF check is 403 with code `csrf_failed` (a missing permission stays `forbidden`). Rate limits key on the rightmost `X-Forwarded-For` entry only when the TCP peer is loopback (Caddy), otherwise on the peer (uvicorn's default `proxy_headers` with `forwarded_allow_ips=127.0.0.1` already rewrites `request.client` to that same entry behind Caddy, so the result is the same either way). The bucket is the IPv4 address or the IPv6 /64 (IPv4-mapped IPv6 counts as IPv4); login and callback are each capped per bucket (20), per IPv6 /56 (40) and per IPv4 /24 or IPv6 /48 (200), all per 10 minutes, finest tier first (a request refused by one tier isn't charged to the wider ones). There is no global cap: a caller's callbacks are live for the transactions it started itself, so a global cap could be exhausted by ten /64s (A1-M1). Pending transactions are capped per bucket (20) and overall (1000); when full, the IPv4 /24 or IPv6 /48 holding the most is picked and its busiest bucket loses its oldest, so a flood spread one transaction per /64 evicts itself, not other users' transactions. Stored/audited addresses are coarsened to IPv4 /24 or IPv6 /48. `/me`'s `zone` is `"pc"` for a direct loopback request and `"internet"` otherwise until the network-zones slice adds `"lan"`. Settings: `BAIHE_GOOGLE_CLIENT_ID`, `BAIHE_GOOGLE_CLIENT_SECRET`, `BAIHE_PUBLIC_URL` (environment or `.env`); missing -> login 503 and `sign_in_configured: false`; a non-https public URL other than localhost is refused at startup. Allowlist from the PC: `python -m api add-user <email>`, `deactivate <email>`, `grant <email> <permission>`.

Requirements carried to step 134 (login), all met by slice A1 above:
- Issue a fresh session from `auth_service.create_session` on every successful login and revoke the client's previous session; never adopt a session id the client sent (session fixation).
- Name the cookie with the `__Host-` prefix (`__Host-baihe_session`: Secure, `Path=/`, no `Domain`) so a sibling subdomain can't plant or overwrite it; keep the loopback-http dev relaxation working (a `__Host-` cookie requires Secure, so dev without TLS needs the plain name).
- Rate-limit the login and callback routes per client address with `SlidingWindowRateLimiter` and audit-log sign-ins.
- Expired sessions are deleted when presented, and at every start of the admin listener with background services on (`auth_service.sweep_stale_sessions`, from the API lifespan): sessions past their absolute or idle expiry and those of a deactivated user go, with their CSRF hashes. Login transactions live in memory only, so a restart leaves none.
